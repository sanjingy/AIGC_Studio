# Architecture Decision Records

> 规则：任何偏离本文档集的实现，必须先提交新的 ADR。
> 代码和文档不一致时，以 ADR 为准，并立即修文档。

---

## ADR-001 Router 与 Director 分离

**决定**：分离。

**原因**：Router 是"路线判断器"，Director 是"项目执行者"，职责完全不同。

---

## ADR-002 Agent 不直接选择具体模型

**决定**：Agent 只声明 capability，Provider Registry 决策实际模型。

**原因**：避免模型变化导致 Agent 代码频繁修改。

---

## ADR-003 ComfyUI 作为 Runtime

**决定**：ComfyUI 属于 Runtime，不属于业务 Agent。

**原因**：未来可接本地、远程、SSH、云 GPU 节点，逻辑不应散落到业务模块。

---

## ADR-004 AutoDL 作为 Cloud Provider

**决定**：AutoDL 只实现 CloudProvider Adapter 接口。

**原因**：未来可加入其他 GPU 平台。**状态：接口预留，方案待定。**

---

## ADR-005 Credits 使用 Ledger

**决定**：不可变交易流水 + reserve / settle / release。

**原因**：防止并发、重试、退款导致余额错误。

---

## ADR-006 Skill 可组合

**决定**：Skill 不是单一 Prompt，而是生产流程定义。

---

## ADR-007 Node Agent 主动连接平台

**决定**：仅采用 outbound connection，**不做平台反向 SSH**。

**原因**：更安全，不需要保管用户长期 SSH 私钥，不需要用户开放入站端口。

**2026-08-16 更新**：原方案的 "MVP 先做入站 SSH、长期改出站" 已取消。
只做出站一种方案，避免产生无法回收的安全债务。

---

## ADR-008 tasks 表是执行状态的唯一权威 ★

**日期**：2026-08-16

**背景**：原设计中同时存在四套状态：LangGraph checkpoint、`tasks.status`、
`agent_runs.status`、以及队列自身的状态。四份真相必然导致
"图认为在跑、表是 failed、前端显示 pending"。

**决定**：

```text
tasks.status              → 执行状态的唯一权威，前端只信它
agent_runs / agent_steps  → 只记录推理过程（审计与回放），不参与状态判断
approvals                 → 只记录人工决策
LangGraph                 → 只做单步无状态推理，不持有跨请求状态
```

**推论**：

- Agent 编排的"下一步是什么"由 Director 每次从 `project_state` 重新计算，
  不依赖内存中的图状态
- 审核门不落在 LangGraph checkpoint 里，落在 `approvals` 表
- 任何进程重启后，系统状态可完全从数据库恢复

**代价**：放弃 LangGraph 的部分便利（如自动 checkpoint 续跑），
换取状态可推理、可排查、可恢复。这笔交易划算。

## ADR-009 模块化单体，而非微服务 ★

**日期**：2026-08-16

**决定**：MVP 阶段后端只有 2 个进程（API + Worker），
领域边界通过目录结构和 import 规则强制，而非进程边界。

**原因**：微服务的成本在当前阶段远大于收益——分布式事务、跨服务调试、
7 套部署与监控。领域边界的价值可以用 lint 规则以极低成本获得。

**退出条件**：当某个模块出现明确的独立扩缩容需求
（如渲染服务需要大量 CPU）时，再单独拆出。届时因为它已经只通过
service 层通信，迁移成本很低。

## ADR-010 队列选型：Arq

**日期**：2026-08-16

**决定**：使用 Arq。原文档的 "Celery/Arq/BullMQ 任选其一" 是未决状态，
未决就是最贵的决定。

**原因**：原生 async 与 FastAPI 同栈、代码量小、Redis 单依赖、
足够支撑当前规模。

**放弃 Celery 的原因**：同步模型与 async 生态摩擦大，配置复杂度高于需要。

**重新评估触发条件**：需要复杂的 DAG 编排或跨语言 Worker 时，
重新评估 Temporal。

---

## ADR-011 音频优先的时间线 ★

**日期**：2026-08-16

**决定**：生产顺序为 `剧本 → TTS → 真实音频时长 → 反推镜头时长 →
关键帧 → 图生视频 → 时间线装配`。

**原因**：视频片段时长固定（5s/10s），台词时长不固定。
先出视频再配音必然音画错位，事后拉伸变形、裁剪丢内容。

**影响**：`03_AgentSystem.md` 和 `04_SkillSpec.md` 的 agents 顺序已相应调整，
Audio 前置到 Image/Video 之前。

---

## ADR-012 一致性引擎是核心模块，不是扩展功能 ★

**日期**：2026-08-16

**决定**：一致性从 `14_FutureExtensibility.md` 提升为独立核心文档
`17_ConsistencyEngine.md`，并在 M1 就交付到 L1 级别。

**原因**：两条。
1. **产品**：用户判断产品可用性的第一标准是角色不变脸，不是剧本质量。
2. **经济**：废片率是成本的唯一主导因素（见 `19_UnitEconomics.md`），
   一致性直接决定单片成本。它是成本中心，不是功能。

## ADR-013 实时通道用 SSE

**日期**：2026-08-16

**决定**：SSE 为主通道，WebSocket 仅用于 Node Agent 长连接。

**原因**：95% 需求是单向下行；SSE 有浏览器原生断线重连；
穿透 Nginx/CDN 更简单。详见 `20_Realtime.md`。

---

## ADR-014 价格与重试系数一律参数化

**日期**：2026-08-16

**决定**：所有上游单价存 `model_pricing`（带生效时间），
所有系数（废片率、overhead、熔断阈值）存 `pricing_rules`，支持热更新。
**代码中不允许出现任何价格常量。**

**原因**：DeepSeek 于 2026-08-17 调价，高峰输出价上涨 350%。
任何硬编码价格的实现会在一夜之间毛利转负。这类事件是常态而非意外。

---

## ADR-015 分级渲染为默认流程

**日期**：2026-08-16

**决定**：`预览档渲染 → 用户确认 → 定稿档渲染` 是默认流程，不是可选项。

**原因**：同时降低成本 35–60% 和提升用户满意度，是本次评审中
性价比最高的一条改动。详见 `19_UnitEconomics.md` 第 3 节。

## ADR-016 架构先行，验证内嵌于 M1

**日期**：2026-08-16

**背景**：评审建议先花 2 周手工做一部片（M0），验证一致性方案与真实废片率，
再开始工程实现。

**决定**：**不采用 M0 作为前置阻塞项。先搭整体架构，
技术验证以 10 镜切片的形式内嵌在 M1 中段。**

**已知代价**（记录在案，不影响执行）：

- 一致性 L1 是否够用，要到 M1 中段才知道；若不够，L2（LoRA）需从 M4 提前
- 废片率在验证前只能用拍值（image 2.5 / video 1.5），
  `19_UnitEconomics.md` 的成本结论在回填前属于估算
- 若验证结论与假设偏差大，部分实现需要返工

**对冲措施**（这是本决定成立的前提，必须落实）：

| 假设 | 对冲 |
|---|---|
| 一致性 L1 够用 | L0–L4 实现为可插拔策略，共享 `ConsistencyStrategy` 接口 |
| 废片率 2.5 / 1.5 | 走 `pricing_rules` 热更新（ADR-014），改数不改码 |
| 5s 一镜、60 镜 | 时间线不假设固定镜头时长（ADR-011） |
| 图生视频漂移可控 | 生成与后处理分离，可插入 L3 修复 |

**额外硬要求**：**可观测性不可推后。**
一致性度量指标（`17_ConsistencyEngine.md` 第 6 节）必须先于一致性策略实现，
`resolved_prompt` 与中间产物从第一天就落库——
否则验证切片跑完也拿不到可用结论。

**验证触发点**：AI Gateway 打通、能真实出图之后立即执行，
不等 M1 全部完成。

## ADR-018 事件序号用 Redis Stream 条目 ID，不自建 INCR 序列

**日期**：2026-08-16

**背景**：`20_Realtime.md` 第 5 节设计的是"Redis INCR 维护 per-project seq +
事件写入 Stream + 客户端带 `Last-Event-ID: <seq>` 重放"。

**决定**：**不自建 seq，直接用 Redis Stream 的条目 ID 作为事件 ID 与重放游标。**

**原因**：Stream 条目 ID（形如 `1734...-0`）本身就是单调递增且全局唯一的，
`XRANGE (last +` 天然实现"从这个位置之后重放"。自建 INCR 会引入两个问题：

1. INCR 与 XADD 是两次独立操作，中间崩溃会产生序号空洞或重复
2. 需要额外维护 seq↔条目 的映射才能定位重放起点

**代价**：事件 ID 不再是人类可读的连续整数。排查时看 `1734...-0` 不如看 `1287`
直观。可接受——它带时间戳，反而更好定位。

**保留不变的部分**：事件信封结构、事件类型清单、`sync.required` 降级、
客户端幂等要求，全部按 `20_Realtime.md` 执行。

## ADR-019 事件投递用 Transactional Outbox

**日期**：2026-08-16

**决定**：状态变更与事件写入放在**同一个数据库事务**里（写 `outbox_events` 表），
由独立的中继循环读出并投递到 Redis Stream。

**原因**：直接在提交后投递会有两种失败：事务回滚了但事件发出去了（前端显示
任务成功、库里其实失败），或事务成功了但投递失败（任务已完成、前端永远转圈）。
两种都是用户可见的严重不一致。

**代价**：多一跳延迟。中继轮询间隔 200ms，实测端到端延迟在可接受范围。

**日期**：2026-08-16

**决定**：全项目由 `AICG` 更正为 `AIGC`（AI Generated Content）。

**范围**：文档目录、文档正文、`aigc-node` CLI、镜像名（`AIGC-ComfyUI-Base` 等）。
