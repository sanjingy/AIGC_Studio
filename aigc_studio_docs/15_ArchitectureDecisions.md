## ADR-001 Router 与 Director 分离

**决定**：分离。

**原因**：Router 是"路线判断器"，Director 是"项目执行者"，职责完全不同。

## ADR-002 Agent 不直接选择具体模型

**决定**：Agent 只声明 capability，Provider Registry 决策实际模型。

**原因**：避免模型变化导致 Agent 代码频繁修改。

## ADR-003 ComfyUI 作为 Runtime

**决定**：ComfyUI 属于 Runtime，不属于业务 Agent。

**原因**：未来可接本地、远程、SSH、云 GPU 节点，逻辑不应散落到业务模块。

## ADR-004 AutoDL 作为 Cloud Provider

**决定**：AutoDL 只实现 CloudProvider Adapter 接口。

**原因**：未来可加入其他 GPU 平台。**状态：接口预留，方案待定。**

## ADR-005 Credits 使用 Ledger

**决定**：不可变交易流水 + reserve / settle / release。

**原因**：防止并发、重试、退款导致余额错误。

## ADR-006 Skill 可组合

**决定**：Skill 不是单一 Prompt，而是生产流程定义。

## ADR-007 Node Agent 主动连接平台

**决定**：仅采用 outbound connection，**不做平台反向 SSH**。

**原因**：更安全，不需要保管用户长期 SSH 私钥，不需要用户开放入站端口。

**2026-08-16 更新**：原方案的 "MVP 先做入站 SSH、长期改出站" 已取消。
只做出站一种方案，避免产生无法回收的安全债务。

## ADR-008 tasks 表是执行状态的唯一权威 ★

**日期**：2026-08-16

**背景**：原设计中同时存在四套状态：LangGraph checkpoint、`tasks.status`、
`agent_runs.status`、以及队列自身的状态。四份真相必然导致
"图认为在跑、表是 failed、前端显示 pending"。

**决定**：

```text
tasks.status              → 执行状态的唯一权威，前端只信它
agent_runs / agent_steps  → 只记录推理过程（审计与回放），不参与状态判断
approvals                 → 只记录人工决策
LangGraph                 → 只做单步无状态推理，不持有跨请求状态
```

**推论**：

- Agent 编排的"下一步是什么"由 Director 每次从 `project_state` 重新计算，
  不依赖内存中的图状态
- 审核门不落在 LangGraph checkpoint 里，落在 `approvals` 表
- 任何进程重启后，系统状态可完全从数据库恢复

**代价**：放弃 LangGraph 的部分便利（如自动 checkpoint 续跑），
换取状态可推理、可排查、可恢复。这笔交易划算。

## ADR-009 模块化单体，而非微服务 ★

**日期**：2026-08-16

**决定**：MVP 阶段后端只有 2 个进程（API + Worker），
领域边界通过目录结构和 import 规则强制，而非进程边界。

**原因**：微服务的成本在当前阶段远大于收益——分布式事务、跨服务调试、
7 套部署与监控。领域边界的价值可以用 lint 规则以极低成本获得。

**退出条件**：当某个模块出现明确的独立扩缩容需求
（如渲染服务需要大量 CPU）时，再单独拆出。届时因为它已经只通过
service 层通信，迁移成本很低。

## ADR-010 队列选型：Arq

**日期**：2026-08-16

**决定**：使用 Arq。原文档的 "Celery/Arq/BullMQ 任选其一" 是未决状态，
未决就是最贵的决定。

**原因**：原生 async 与 FastAPI 同栈、代码量小、Redis 单依赖、
足够支撑当前规模。

**放弃 Celery 的原因**：同步模型与 async 生态摩擦大，配置复杂度高于需要。

**重新评估触发条件**：需要复杂的 DAG 编排或跨语言 Worker 时，
重新评估 Temporal。

## ADR-011 音频优先的时间线 ★

**日期**：2026-08-16

**决定**：生产顺序为 `剧本 → TTS → 真实音频时长 → 反推镜头时长 →
关键帧 → 图生视频 → 时间线装配`。

**原因**：视频片段时长固定（5s/10s），台词时长不固定。
先出视频再配音必然音画错位，事后拉伸变形、裁剪丢内容。

**影响**：`03_AgentSystem.md` 和 `04_SkillSpec.md` 的 agents 顺序已相应调整，
Audio 前置到 Image/Video 之前。

## ADR-012 一致性引擎是核心模块，不是扩展功能 ★

**日期**：2026-08-16

**决定**：一致性从 `14_FutureExtensibility.md` 提升为独立核心文档
`17_ConsistencyEngine.md`，并在 M1 就交付到 L1 级别。

**原因**：两条。
1. **产品**：用户判断产品可用性的第一标准是角色不变脸，不是剧本质量。
2. **经济**：废片率是成本的唯一主导因素（见 `19_UnitEconomics.md`），
   一致性直接决定单片成本。它是成本中心，不是功能。

**日期**：2026-08-16

**决定**：SSE 为主通道，WebSocket 仅用于 Node Agent 长连接。

**原因**：95% 需求是单向下行；SSE 有浏览器原生断线重连；

## ADR-014 价格与重试系数一律参数化

**日期**：2026-08-16

**决定**：所有上游单价存 `model_pricing`（带生效时间），
所有系数（废片率、overhead、熔断阈值）存 `pricing_rules`，支持热更新。
**代码中不允许出现任何价格常量。**

**原因**：DeepSeek 于 2026-08-17 调价，高峰输出价上涨 350%。
任何硬编码价格的实现会在一夜之间毛利转负。这类事件是常态而非意外。

## ADR-015 分级渲染为默认流程

**日期**：2026-08-16

**决定**：`预览档渲染 → 用户确认 → 定稿档渲染` 是默认流程，不是可选项。

**原因**：同时降低成本 35–60% 和提升用户满意度，是本次评审中
性价比最高的一条改动。详见 `19_UnitEconomics.md` 第 3 节。

## ADR-016 架构先行，验证内嵌于 M1

**日期**：2026-08-16

**背景**：评审建议先花 2 周手工做一部片（M0），验证一致性方案与真实废片率，
再开始工程实现。

**决定**：**不采用 M0 作为前置阻塞项。先搭整体架构，
技术验证以 10 镜切片的形式内嵌在 M1 中段。**

**已知代价**（记录在案，不影响执行）：

- 一致性 L1 是否够用，要到 M1 中段才知道；若不够，L2（LoRA）需从 M4 提前
- 废片率在验证前只能用拍值（image 2.5 / video 1.5），
  `19_UnitEconomics.md` 的成本结论在回填前属于估算
- 若验证结论与假设偏差大，部分实现需要返工

**对冲措施**（这是本决定成立的前提，必须落实）：

| 假设 | 对冲 |
|---|---|
| 一致性 L1 够用 | L0–L4 实现为可插拔策略，共享 `ConsistencyStrategy` 接口 |
| 废片率 2.5 / 1.5 | 走 `pricing_rules` 热更新（ADR-014），改数不改码 |
| 5s 一镜、60 镜 | 时间线不假设固定镜头时长（ADR-011） |
| 图生视频漂移可控 | 生成与后处理分离，可插入 L3 修复 |

**额外硬要求**：**可观测性不可推后。**
一致性度量指标（`17_ConsistencyEngine.md` 第 6 节）必须先于一致性策略实现，
`resolved_prompt` 与中间产物从第一天就落库——
否则验证切片跑完也拿不到可用结论。

**验证触发点**：AI Gateway 打通、能真实出图之后立即执行，
不等 M1 全部完成。

## ADR-018 事件序号用 Redis Stream 条目 ID，不自建 INCR 序列

**日期**：2026-08-16

**背景**：`20_Realtime.md` 第 5 节设计的是"Redis INCR 维护 per-project seq +
事件写入 Stream + 客户端带 `Last-Event-ID: <seq>` 重放"。

**决定**：**不自建 seq，直接用 Redis Stream 的条目 ID 作为事件 ID 与重放游标。**

**原因**：Stream 条目 ID（形如 `1734...-0`）本身就是单调递增且全局唯一的，
`XRANGE (last +` 天然实现"从这个位置之后重放"。自建 INCR 会引入两个问题：

1. INCR 与 XADD 是两次独立操作，中间崩溃会产生序号空洞或重复
2. 需要额外维护 seq↔条目 的映射才能定位重放起点

**代价**：事件 ID 不再是人类可读的连续整数。排查时看 `1734...-0` 不如看 `1287`
直观。可接受——它带时间戳，反而更好定位。

**保留不变的部分**：事件信封结构、事件类型清单、`sync.required` 降级、
客户端幂等要求，全部按 `20_Realtime.md` 执行。

## ADR-019 事件投递用 Transactional Outbox

**日期**：2026-08-16

**决定**：状态变更与事件写入放在**同一个数据库事务**里（写 `outbox_events` 表），
由独立的中继循环读出并投递到 Redis Stream。

**原因**：直接在提交后投递会有两种失败：事务回滚了但事件发出去了（前端显示
任务成功、库里其实失败），或事务成功了但投递失败（任务已完成、前端永远转圈）。
两种都是用户可见的严重不一致。

**代价**：多一跳延迟。中继轮询间隔 200ms，实测端到端延迟在可接受范围。

## ADR-020 Skill 是声明式生产模板，由平台运行时解释执行 ★

**日期**：2026-08-18

**决定**：Skill 落成 `skills/*.yaml` 的声明，结构为
**阶段序列 + 门 + 审查策略 + 导出布局**。四种阶段类型：

| kind | 含义 | 约束 |
|---|---|---|
| `agent` | 一次 LLM 调用 | 声明 role，可钉死到具体 Agent id |
| `compute` | 确定性代码 | 只能引用 `KNOWN_HANDLERS` 白名单里的处理器 |
| `generate` | 出图/出音/出视频 | 必须声明 review 策略 |
| `gate` | 阻塞门 | 只能是 `KNOWN_GATES` 里的五道之一 |

**原因**：三份成熟的第三方提示词（小说改编 / 美术指导 / 分镜导演）跨了三层：
提示词本身该是 Agent，时长与批次计算该是确定性代码，
"画风确认 → 分镜确认 → 锚点卡确认"该是门。任何一层单独承接都装不下——
一个 `AgentSpec` 只有一份 prompt、一个 output_schema、`max_steps ≤ 20`，
塞进整条生产线会得到一个既不可测试也不可回归的巨物，
而 `agents/spec.py` 的四重约束对它形同虚设。

**Skill 只能是声明，不能是代码**，理由与 Agent 完全相同，
且攻击面更大：Skill 还会往用户指定的本地目录写文件。
所以处理器走白名单，导出路径按段白名单校验（不做"替换危险字符"式清洗——
清洗永远漏，白名单不会）。

**阶段顺序上的一处刻意偏离**：语音合成排在视觉资产**之前**。
剧本定稿时台词就定了，此刻合成能拿到每句真实时长，
分镜表的时长与 15 秒批次从第一次算就是真值，不需要事后回填。
这是 ADR-011 音频优先的直接推论，第三方提示词里没有这一步，
因为它们的终点是人肉复制粘贴。

**代价**：多一层间接。调试"为什么这一步没跑"要同时看 Skill 声明和 Agent 声明。
换来的是同一个 role 下能并存多个 Agent（改编 / 洗稿、角色 / 场景 / 分镜），
而 `registry.default_for(role)` 只能取一个。

**状态**：spec + registry + 默认 Skill 已落地并有测试；
**运行时（解释执行）尚未接线**，`skill.novel_to_anime.v1` 为 `draft`。

## ADR-021 门的数量是策略，不是常量

**日期**：2026-08-18

**决定**：门由 Skill 声明，每道门有 `required` 标志。
默认 Skill 声明五道：`script` / `assets` / `anchor` / `storyboard` / `final`，
其中 `script` 与 `final` 为 `required`，用户不能关。
全自动模式下实际只剩这两道。

**原因**：`01_ProductSpec.md` 定的三道固定门和
"门开得越多用户流失越快"都是对的，但**它们描述的是默认值，不是上限**。
批量生产的用户要的是两道，第一次用的用户要的是五道。
写死在 `orchestrator._GATE_OF` 里，两类用户只能满足一类。

`script` 不可关：后面每一分钱都花在这份剧本上，
用户没看过就往下跑，错了要从头再来。
`final` 不可关：没人看过的成片不该算交付。

**代价**：`approvals` 的 gate 取值从 3 种变为 5 种，
原 `setup` 拆成 `script` + `assets`。接线时需要一次数据迁移。

## ADR-022 本地资产目录是镜像，对象存储仍是唯一真相

**日期**：2026-08-18

**决定**：创建项目时可指定本地目录，每阶段产出自动落一份过去。
**MinIO/S3 仍是唯一真相**，本地目录是单向镜像。
目录布局由 Skill 的 `export` 字段声明，布局版本号存在 Skill 里。

**原因**：用户要能直接打开文件夹拿素材，这个诉求是真实的。
但反过来做（本地为真相）会连带废掉断点续跑、跨设备、协作和资产版本追溯，
而这些都是已经建成的能力。

浏览器写不了任意本地路径，落盘有两条路：
File System Access API（Chromium，授权一次，标签页关了就停）
或轻量本地同步器（更稳，也是将来做桌面客户端的路）。**同步器方案待定。**

**代价**：本地目录可能与对象存储不一致（用户手动删了文件）。
不做双向同步，也不以本地文件为准恢复——不一致时以对象存储重新落一份。

## ADR-023 审查模式三档，默认半自动

**日期**：2026-08-18

**决定**：出图/出视频阶段声明 `review` 策略，用户在项目级选三档之一：

| 模式 | 判定者 | 不合格时 |
|---|---|---|
| `manual` | 用户 | 用户改提示词重生 |
| `assisted` | AI 筛 + 用户裁 | 只把 AI 判不合格的推给用户 |
| `auto` | AI 打分 vs 阈值 | 自动重试，超 `max_attempts` 则停下问人 |

允许 `auto` 的阶段**必须**声明 `metric` 与 `threshold_key`。
**阈值只写键名，数值进库**——理由同 ADR-014：
相似度阈值仍在标定中，写死在会被分发的 YAML 里等于把待定数字冻起来。

**原因**：`consistency/metrics.py` 的实测数据已经证明单一全局阈值必然误判——
构图差异对整图 embedding 的影响和身份差异是同一个量级，
0.75 会把所有远景和特写都判成"角色崩了"。中间地带交人工是有数据支撑的默认值，
不是保守。

场景概念图没有基准图可比，现阶段 `allow_auto: false`；
TTS 没有可计算的音质指标，同样不开放全自动——
那只会变成"没人听过就发出去了"。

**代价**：半自动仍需用户参与，达不到"睡一觉起来片子好了"。
等人工判定数据积累够，用它反过来标定阈值，再逐阶段放开 `auto`。

## ADR-024 模型选择在项目级覆盖，Agent 仍不选模型

**日期**：2026-08-18

**决定**：用户可在项目级按 **capability** 覆盖模型
（`project.model_preference`），Gateway 解析时优先读覆盖。
Skill 用 `model_policy.user_selectable` 声明哪些能力可由用户改。

**ADR-002 不变**：Agent 仍然只声明 capability，不指定具体模型。
覆盖发生在项目层，不在 Agent 层。

**原因**：用户要"便宜点"或"好看点"是合理诉求，
但让 Agent spec 写死模型会让每次上游调价都要改 spec。

**两条硬约束**：

1. **换模型必须重算 Credits 预估**，走 `model_pricing` 表，不沿用旧数字
2. **部分 role 禁用推理模型**（`model_policy.no_reasoning_roles`）。
   `deepseek-v4-*` 的思考 token 计入输出预算，用在分类和结构化抽取上
   会返回**空内容且不报错**——已踩过两次

**代价**：暴露给普通用户的应是**档位**（经济/标准/高质）而非模型 ID。
档位到模型的映射是另一张表，尚未建。

## ADR-025 用户自带 Key（BYOK）走大幅折扣，不是免费也不是全价 ★

**日期**：2026-08-18

**背景**：用户要求"在配置页面直接配自己的模型 Key"。这会直接冲击
`19_UnitEconomics.md` 的毛利模型——那份文档从头到尾假设的是
"平台用自己的 Key 转发调用、赚上游成本与售价的差"。用户自带 Key 时，
平台不再承担 `provider_cost`，但**没有停止承担别的成本**：
存储、CDN、审核、系统故障重跑计提——这些是 `19_UnitEconomics.md` 1.5 节
"隐性成本"，跟调用哪个 Key 无关，BYOK 不能让这部分也变成免费。

**决定**：

1. 项目/用户配置了某个 capability 的自有 Key 时，该 capability 的
   Credits 预估**跳过 `model_pricing` 里的 `provider_cost` 加价部分**，
   只按 `19_UnitEconomics.md` 1.5 节的隐性成本档位收一笔小额 Credits
   （具体数值走 `pricing_rules`，不写死——理由同 ADR-014）。
   不是完全免费：完全免费等于邀请用户拿自己的免费/低价 Key
   无限占用平台存储和计算，免费额度设计（`19_UnitEconomics.md` 第 5 节）
   会被绕过。
2. **用户资产库的 1GB 配额（见项目页面另附）天然是第二道防线**：
   即使 Credits 侧几乎不花钱，存储侧的物理上限仍然卡着，
   不需要为 BYOK 单独再造一套滥用检测。
3. Key 走 `_encrypted` 字段（应用层 AES-GCM，`09_Database.md` §附录
   已有约定的加密字段命名规范），只在 Gateway 解密后用于当次请求，
   不回显给前端、不进日志、不进 `input_json`——这条是 CLAUDE.md
   "密钥不进代码、不进日志、不进 input_json" 的直接推论，没有新增例外。
4. 用户可为哪些 capability 配自己的 Key，由 Skill 的
   `model_policy.user_selectable` 决定（复用 ADR-024 已有的开关，
   不新开一套声明）。

**原因**：全价计费会让"自带 Key"这个功能对用户毫无吸引力
（花钱买了自己的 Key 又要付平台全价，等于白花钱）；完全免费会让
`19_UnitEconomics.md` 的免费额度设计形同虚设，且给了刷子低成本
占用平台资源的空子。折扣但不免费，两头都保。

**代价**：`billing/pricing.py` 的估价公式要多一个分支
（"这个 capability 是不是走了用户自己的 Key"），实现前需要先给
`model_pricing`/`pricing_rules` 加对应的折扣系数键名。

## ADR-026 Skill 上传本轮只做到"能传、能选"，不接运行时

**日期**：2026-08-18

**背景**：`12_MVP_Roadmap.md` 把"用户自定义 Skill"排在 **M5（Skill 生态）**，
比当前所在的 M2 晚三个里程碑；`2026-08-18 进度与开发计划.md` 也明确写
"Skill 运行时之前不要做，阶段图还在频繁变，固化太早只会白改两遍"。
用户这次要求提前做"上传 Skill、切换 Skill"这个面向终端用户的功能。

**决定**：本轮只做到**上传、校验、项目内选择**，不做**运行时接线**：

- 用户可以上传 Skill YAML（走 `04_SkillSpec.md` §7 已定的白名单校验：
  处理器白名单、导出路径白名单、门白名单、能力白名单、重试次数上限——
  这套校验本来就是为"不可信输入"设计的，本轮直接复用，不新增豁免）
- 项目里可以选择"用哪个 Skill"，选择被存下来
- **选了非默认 Skill 时，生产流程实际上仍然走 `orchestrator._NEXT`
  硬编码的阶段图**，跟 ADR-020 记录的现状一致——选择目前不生效，
  界面要如实标注（比如"预览"或"即将支持"），不能假装已经生效

**原因**：真正让"切换 Skill"生效，需要把 `orchestrator._NEXT` 从硬编码
搬到读 Skill 声明驱动，这项工作量与 M2 本身（TTS/时间线/ffmpeg）相当，
而 M2 阶段图现在还会因为出片链路继续变——现在接线等于要为同一张图改
两遍。上传与选择的 UI/数据层可以先做且不受这个影响：Skill 记录、
校验逻辑、选择状态都是稳定的，不会因为阶段图变化而返工。

**代价**：用户能上传 Skill，但上传了也暂时看不到效果——这是本轮
刻意留下的半成品，验收标准里必须包含"UI 明确告知运行时未接线"，
不能做成一个看起来能用、实际不生效的功能。运行时接线本身留到
阶段图随 M2 稳定之后，作为独立一轮做，到时候再补一条 ADR。

## ADR-027 自带 Key 的调用与熔断按 org 独立，且不回落平台 Key ★

**日期**：2026-08-19

**背景**：ADR-025 把 BYOK 的**计费**做完了——配了自有 Key 的能力按隐性成本
档位收费，跳过 `model_pricing` 的 provider_cost 加价。但 Gateway 的
`_build()` 仍然是进程启动时读一次环境变量、建一张平台 Key 的路由表，
**实际调用用的还是平台的 Key**。于是每一次 BYOK 生成都是：用户按折扣价付款、
平台按全价掏钱买上游。差额没有任何告警，账上只体现为毛利莫名其妙地掉。

**决定**：

1. Key 的解析从"进程启动时读一次环境变量"改成"每次调用按
   `org_id + capability` 现查"。查到就用那把（`KeySource.ORG`），
   查不到落回平台路由表（`KeySource.PLATFORM`，行为与本 ADR 之前完全一致）。
   **不缓存**：缓存等于"删了 Key 还在用"，而删 Key 的人多半正是因为它泄露了。
   代价是每次生成多一次带索引的单行查询加一次 AES-GCM 解密，
   相对一次几秒到几十秒的生成可以忽略。
2. **熔断按账号分作用域**：平台档一个，每个自带 Key 的 org 各一个。
   合起来算两个方向都错——一个用户的 Key 被上游封了会把整家 Provider
   熔断掉、把所有用平台 Key 的人一起降级；反过来平台账号出问题时
   拦住用自己 Key 的用户同样没道理，那是另一个账号。
3. **BYOK 不跨 Provider failover，尤其不回落平台 Key**。用户只配了一家，
   "轮换到另一家"这个选项不存在；回落平台 Key 则是把第 1 条要堵的洞
   原样搬到了失败路径上。同一把 Key 换模型仍然允许（同账号同价），
   但账号级失败（鉴权、欠费）连模型都不换。
4. 自有 Key 失败时报 `provider.byok.rejected`，而不是把上游的
   `provider.account.insufficient` 原样透出去：后者的用户文案是
   "服务暂时不可用，请稍后重试"，而这种情况等下去永远不会好，
   只有用户自己能修。上游的具体分类留在 `detail.upstream_code`，
   沿用 ADR-025"测试连接"那套，不另造一份。透出前必须过一遍脱敏——
   上游 401 常把收到的 Key 原样贴回来，而这条 message 会被写进
   `agent_runs.error_detail`。
5. 适配器每次调用记一条 `provider.call` 信号，带 `key_source` 枚举
   （**只有枚举，没有 Key、没有尾号、没有密文**）。它是唯一能证明
   "确实用了自有 Key"的东西：计费查的是库里有没有那一行，调用用的是解出来的
   那把 Key，两者完全可能背离——本 ADR 之前正是背离状态。

**原因**：第 1 条是止血，后面四条都是它的直接推论。真正的判断题只有
第 3 条：回落平台看起来对用户更友好（他的 Key 坏了也照样出片），
但那正是重新打开财务漏洞的做法，而且把"你的 Key 坏了"这个只有用户能修的
问题永久藏了起来。

**代价**：

- 每次生成多一次 DB 查询 + 一次解密。
- 用户自己的 Key 坏掉时生成会失败，而不是静默降级——这是刻意的，
  但要求设置页的"测试连接"足够好用，否则用户会卡在"为什么突然不能生成了"。
- 熔断作用域按 org 分之后，Redis 里的 `cb:provider:*` 键数量随自带 Key
  的 org 数增长。键本身带 TTL（失败窗口的 4 倍），不会无限堆积。

## ADR-028 资产库分类用独立关联表；参考描述生成角色复用同一个 Agent，另存一张表 ★

**日期**：2026-08-19

**背景**：借鉴同类产品（AgentCine）的资产库做两件事：用户能自建文件夹给
资产归类；能直接写一段角色描述就得到一份正式角色档案，不必先建项目、
先传小说、先跑完路由和剧本。第二件事撞上了一个既有假设——**角色档案跟着
项目走**。现有实现里它们存在 `agent_runs.output_json`，而
`agent_runs.project_id` 是 NOT NULL，资产库、项目详情、编排器全都按项目查它。
（它的多套外观变体 appearances 本轮不做：那依赖真实出图，而出图还没接进
生产链路，等 M2 之后再说。）

**决定**：

1. **归类关系走独立的 `asset_folder_items`，不给任何现有表加 `folder_id` 列。**
   要归类的四种东西里，角色/场景档案存在 agent 模块的表上——asset 模块不能
   往别的模块的表上加列（ADR-009）。一张关联表让四种东西走同一套归类逻辑，
   且不动任何现有表结构。一个条目同时只属于一个文件夹：多重归类的收益
   远小于"这份档案到底在哪"的困惑。关系行硬删（它没有审计价值），
   文件夹软删。
2. **文件夹属于用户，不属于项目。** 资产库本身就是跨项目的（配额按账号算），
   分类挂到项目上会让"配角参考"在每个项目里各存一份。
3. **独立角色档案另起 `character_entries`，不把 `agent_runs.project_id` 改成可空。**
   松一条被四处依赖的 NOT NULL 约束，等于让所有"按项目查档案"的代码都要
   重新考虑 NULL 的语义；而新加一张表谁都不影响。代价是"角色档案"在库里
   有两个存处，靠 output 是同一个 `CharacterSheets` schema 把它们钉在一起。
4. **复用 `visual.character.v1`，不新增"简易版角色 Agent"。** 输入形态不同
   （参考描述 vs 剧本），要产出的东西完全一样。两份相似的角色提示词一定会
   分叉——改了一处忘了另一处，两条入口生成的角色就不是一个标准，
   而这正是 ADR-020 拆三份提示词时要避免的失败模式（拆开的是**职责不同**的
   提示词，不是同一职责的两个副本）。输入形态的差异由 `system_suffix` 抹平，
   和聊天修订用的是同一个机制。
5. **`runner` 拆出 `complete_structured`**：提示词合成 + 输出契约 + schema
   校验 + 重试，不碰数据库；`run_agent` 在它外面套一层落 `agent_runs` /
   `agent_steps`。不挂项目的调用只用内核那一半，把过程存进自己的表。
   两条路径共用同一套约束，spec 的四重限制一条都没被绕开。
6. **同步 Agent 调用照常走 Credits 预扣/结算**，预扣额取 spec 的
   `budget_credits`（它本来就是"单次运行成本上限"），结算按实际输出 token
   查 `model_pricing`，差额退回。流水的 `ref_type` 记 `character_entry`，
   不写 `task`——指向一个不存在的 task 会让对账查不下去。

**原因**：第 1、3 条是同一个判断的两面——**为一个新入口去松既有约束，
风险远大于多一张表**。第 4、5 条是同一个判断的两面——**共用提示词，
不共用存储**。

**代价**：

- 归类关系与被归类的东西之间没有外键（跨模块不能加），删掉一个资产时
  关系行会变成孤儿。目前只在删角色档案时顺手清理；孤儿行不影响展示
  （列表是从实体侧查出来再打标的），但需要一个定期清理任务，记在 M2。
- 文件夹视图不分页。容量由 `MAX_FOLDER_ITEMS` 封顶；先分页再按归类过滤
  会得到一页空结果，那比不分页糟得多。
- 生成的独立角色档案**还不能被项目的生产流程消费**——那需要设计外部角色
  档案怎么进 `current_state_json`，超出本轮范围。前端照 ADR-026 的做法
  明确标注"未接生产流程"，不做一个看起来能用的按钮。
- 结算金额向上取整（不足 1 Credit 按 1 收）。向下取整会让一次约 600 个
  输出 token 的调用收 0（2026-08-19 真机验证发现），那是系统性漏收。
