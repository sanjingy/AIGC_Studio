## ADR-001 Router 与 Director 分离

**决定**：分离。

**原因**：Router 是"路线判断器"，Director 是"项目执行者"，职责完全不同。

## ADR-002 Agent 不直接选择具体模型

**决定**：Agent 只声明 capability，Provider Registry 决策实际模型。

**原因**：避免模型变化导致 Agent 代码频繁修改。

**决定**：ComfyUI 属于 Runtime，不属于业务 Agent。

**原因**：未来可接本地、远程、SSH、云 GPU 节点，逻辑不应散落到业务模块。

**决定**：AutoDL 只实现 CloudProvider Adapter 接口。

**原因**：未来可加入其他 GPU 平台。**状态：接口预留，方案待定。**

## ADR-005 Credits 使用 Ledger

**决定**：不可变交易流水 + reserve / settle / release。

**原因**：防止并发、重试、退款导致余额错误。

## ADR-006 Skill 可组合

**决定**：Skill 不是单一 Prompt，而是生产流程定义。

## ADR-007 Node Agent 主动连接平台

**决定**：仅采用 outbound connection，**不做平台反向 SSH**。

**原因**：更安全，不需要保管用户长期 SSH 私钥，不需要用户开放入站端口。

**2026-08-16 更新**：原方案的 "MVP 先做入站 SSH、长期改出站" 已取消。
只做出站一种方案，避免产生无法回收的安全债务。

## ADR-008 tasks 表是执行状态的唯一权威 ★

**日期**：2026-08-16

**背景**：原设计中同时存在四套状态：LangGraph checkpoint、`tasks.status`、
`agent_runs.status`、以及队列自身的状态。四份真相必然导致
"图认为在跑、表是 failed、前端显示 pending"。

**决定**：

```text
tasks.status              → 执行状态的唯一权威，前端只信它
agent_runs / agent_steps  → 只记录推理过程（审计与回放），不参与状态判断
approvals                 → 只记录人工决策
LangGraph                 → 只做单步无状态推理，不持有跨请求状态
```

**推论**：

- Agent 编排的"下一步是什么"由 Director 每次从 `project_state` 重新计算，
  不依赖内存中的图状态
- 审核门不落在 LangGraph checkpoint 里，落在 `approvals` 表
- 任何进程重启后，系统状态可完全从数据库恢复

**代价**：放弃 LangGraph 的部分便利（如自动 checkpoint 续跑），
换取状态可推理、可排查、可恢复。这笔交易划算。

## ADR-009 模块化单体，而非微服务 ★

**日期**：2026-08-16

**决定**：MVP 阶段后端只有 2 个进程（API + Worker），
领域边界通过目录结构和 import 规则强制，而非进程边界。

**原因**：微服务的成本在当前阶段远大于收益——分布式事务、跨服务调试、
7 套部署与监控。领域边界的价值可以用 lint 规则以极低成本获得。

**退出条件**：当某个模块出现明确的独立扩缩容需求
（如渲染服务需要大量 CPU）时，再单独拆出。届时因为它已经只通过
service 层通信，迁移成本很低。

## ADR-010 队列选型：Arq

**日期**：2026-08-16

**决定**：使用 Arq。原文档的 "Celery/Arq/BullMQ 任选其一" 是未决状态，
未决就是最贵的决定。

**原因**：原生 async 与 FastAPI 同栈、代码量小、Redis 单依赖、
足够支撑当前规模。

**放弃 Celery 的原因**：同步模型与 async 生态摩擦大，配置复杂度高于需要。

**重新评估触发条件**：需要复杂的 DAG 编排或跨语言 Worker 时，
重新评估 Temporal。

## ADR-011 音频优先的时间线 ★

**日期**：2026-08-16

**决定**：生产顺序为 `剧本 → TTS → 真实音频时长 → 反推镜头时长 →
关键帧 → 图生视频 → 时间线装配`。

**原因**：视频片段时长固定（5s/10s），台词时长不固定。
先出视频再配音必然音画错位，事后拉伸变形、裁剪丢内容。

**影响**：`03_AgentSystem.md` 和 `04_SkillSpec.md` 的 agents 顺序已相应调整，
Audio 前置到 Image/Video 之前。

## ADR-012 一致性引擎是核心模块，不是扩展功能 ★

**日期**：2026-08-16

**决定**：一致性从 `14_FutureExtensibility.md` 提升为独立核心文档
`17_ConsistencyEngine.md`，并在 M1 就交付到 L1 级别。

**原因**：两条。
1. **产品**：用户判断产品可用性的第一标准是角色不变脸，不是剧本质量。
2. **经济**：废片率是成本的唯一主导因素（见 `19_UnitEconomics.md`），
   一致性直接决定单片成本。它是成本中心，不是功能。

**日期**：2026-08-16

**决定**：SSE 为主通道，WebSocket 仅用于 Node Agent 长连接。

**原因**：95% 需求是单向下行；SSE 有浏览器原生断线重连；

## ADR-014 价格与重试系数一律参数化

**日期**：2026-08-16

**决定**：所有上游单价存 `model_pricing`（带生效时间），
所有系数（废片率、overhead、熔断阈值）存 `pricing_rules`，支持热更新。
**代码中不允许出现任何价格常量。**

**原因**：DeepSeek 于 2026-08-17 调价，高峰输出价上涨 350%。
任何硬编码价格的实现会在一夜之间毛利转负。这类事件是常态而非意外。

## ADR-015 分级渲染为默认流程

**日期**：2026-08-16

**决定**：`预览档渲染 → 用户确认 → 定稿档渲染` 是默认流程，不是可选项。

**原因**：同时降低成本 35–60% 和提升用户满意度，是本次评审中
性价比最高的一条改动。详见 `19_UnitEconomics.md` 第 3 节。

## ADR-016 架构先行，验证内嵌于 M1

**日期**：2026-08-16

**背景**：评审建议先花 2 周手工做一部片（M0），验证一致性方案与真实废片率，
再开始工程实现。

**决定**：**不采用 M0 作为前置阻塞项。先搭整体架构，
技术验证以 10 镜切片的形式内嵌在 M1 中段。**

**已知代价**（记录在案，不影响执行）：

- 一致性 L1 是否够用，要到 M1 中段才知道；若不够，L2（LoRA）需从 M4 提前
- 废片率在验证前只能用拍值（image 2.5 / video 1.5），
  `19_UnitEconomics.md` 的成本结论在回填前属于估算
- 若验证结论与假设偏差大，部分实现需要返工

**对冲措施**（这是本决定成立的前提，必须落实）：

| 假设 | 对冲 |
|---|---|
| 一致性 L1 够用 | L0–L4 实现为可插拔策略，共享 `ConsistencyStrategy` 接口 |
| 废片率 2.5 / 1.5 | 走 `pricing_rules` 热更新（ADR-014），改数不改码 |
| 5s 一镜、60 镜 | 时间线不假设固定镜头时长（ADR-011） |
| 图生视频漂移可控 | 生成与后处理分离，可插入 L3 修复 |

**额外硬要求**：**可观测性不可推后。**
一致性度量指标（`17_ConsistencyEngine.md` 第 6 节）必须先于一致性策略实现，
`resolved_prompt` 与中间产物从第一天就落库——
否则验证切片跑完也拿不到可用结论。

**验证触发点**：AI Gateway 打通、能真实出图之后立即执行，
不等 M1 全部完成。

## ADR-018 事件序号用 Redis Stream 条目 ID，不自建 INCR 序列

**日期**：2026-08-16

**背景**：`20_Realtime.md` 第 5 节设计的是"Redis INCR 维护 per-project seq +
事件写入 Stream + 客户端带 `Last-Event-ID: <seq>` 重放"。

**决定**：**不自建 seq，直接用 Redis Stream 的条目 ID 作为事件 ID 与重放游标。**

**原因**：Stream 条目 ID（形如 `1734...-0`）本身就是单调递增且全局唯一的，
`XRANGE (last +` 天然实现"从这个位置之后重放"。自建 INCR 会引入两个问题：

1. INCR 与 XADD 是两次独立操作，中间崩溃会产生序号空洞或重复
2. 需要额外维护 seq↔条目 的映射才能定位重放起点

**代价**：事件 ID 不再是人类可读的连续整数。排查时看 `1734...-0` 不如看 `1287`
直观。可接受——它带时间戳，反而更好定位。

**保留不变的部分**：事件信封结构、事件类型清单、`sync.required` 降级、
客户端幂等要求，全部按 `20_Realtime.md` 执行。

## ADR-019 事件投递用 Transactional Outbox

**日期**：2026-08-16

**决定**：状态变更与事件写入放在**同一个数据库事务**里（写 `outbox_events` 表），
由独立的中继循环读出并投递到 Redis Stream。

**原因**：直接在提交后投递会有两种失败：事务回滚了但事件发出去了（前端显示
任务成功、库里其实失败），或事务成功了但投递失败（任务已完成、前端永远转圈）。
两种都是用户可见的严重不一致。

**代价**：多一跳延迟。中继轮询间隔 200ms，实测端到端延迟在可接受范围。

## ADR-020 Skill 是声明式生产模板，由平台运行时解释执行 ★

**日期**：2026-08-18

**决定**：Skill 落成 `skills/*.yaml` 的声明，结构为
**阶段序列 + 门 + 审查策略 + 导出布局**。四种阶段类型：

| kind | 含义 | 约束 |
|---|---|---|
| `agent` | 一次 LLM 调用 | 声明 role，可钉死到具体 Agent id |
| `compute` | 确定性代码 | 只能引用 `KNOWN_HANDLERS` 白名单里的处理器 |
| `generate` | 出图/出音/出视频 | 必须声明 review 策略 |
| `gate` | 阻塞门 | 只能是 `KNOWN_GATES` 里的五道之一 |

**原因**：三份成熟的第三方提示词（小说改编 / 美术指导 / 分镜导演）跨了三层：
提示词本身该是 Agent，时长与批次计算该是确定性代码，
"画风确认 → 分镜确认 → 锚点卡确认"该是门。任何一层单独承接都装不下——
一个 `AgentSpec` 只有一份 prompt、一个 output_schema、`max_steps ≤ 20`，
塞进整条生产线会得到一个既不可测试也不可回归的巨物，
而 `agents/spec.py` 的四重约束对它形同虚设。

**Skill 只能是声明，不能是代码**，理由与 Agent 完全相同，
且攻击面更大：Skill 还会往用户指定的本地目录写文件。
所以处理器走白名单，导出路径按段白名单校验（不做"替换危险字符"式清洗——
清洗永远漏，白名单不会）。

**阶段顺序上的一处刻意偏离**：语音合成排在视觉资产**之前**。
剧本定稿时台词就定了，此刻合成能拿到每句真实时长，
分镜表的时长与 15 秒批次从第一次算就是真值，不需要事后回填。
这是 ADR-011 音频优先的直接推论，第三方提示词里没有这一步，
因为它们的终点是人肉复制粘贴。

**代价**：多一层间接。调试"为什么这一步没跑"要同时看 Skill 声明和 Agent 声明。
换来的是同一个 role 下能并存多个 Agent（改编 / 洗稿、角色 / 场景 / 分镜），
而 `registry.default_for(role)` 只能取一个。

**状态**：spec + registry + 默认 Skill 已落地并有测试；
**运行时（解释执行）尚未接线**，`skill.novel_to_anime.v1` 为 `draft`。

## ADR-021 门的数量是策略，不是常量

**日期**：2026-08-18

**决定**：门由 Skill 声明，每道门有 `required` 标志。
默认 Skill 声明五道：`script` / `assets` / `anchor` / `storyboard` / `final`，
其中 `script` 与 `final` 为 `required`，用户不能关。
全自动模式下实际只剩这两道。

**原因**：`01_ProductSpec.md` 定的三道固定门和
"门开得越多用户流失越快"都是对的，但**它们描述的是默认值，不是上限**。
批量生产的用户要的是两道，第一次用的用户要的是五道。
写死在 `orchestrator._GATE_OF` 里，两类用户只能满足一类。

`script` 不可关：后面每一分钱都花在这份剧本上，
用户没看过就往下跑，错了要从头再来。
`final` 不可关：没人看过的成片不该算交付。

**代价**：`approvals` 的 gate 取值从 3 种变为 5 种，
原 `setup` 拆成 `script` + `assets`。接线时需要一次数据迁移。

## ADR-022 本地资产目录是镜像，对象存储仍是唯一真相

**日期**：2026-08-18

**决定**：创建项目时可指定本地目录，每阶段产出自动落一份过去。
**MinIO/S3 仍是唯一真相**，本地目录是单向镜像。
目录布局由 Skill 的 `export` 字段声明，布局版本号存在 Skill 里。

**原因**：用户要能直接打开文件夹拿素材，这个诉求是真实的。
但反过来做（本地为真相）会连带废掉断点续跑、跨设备、协作和资产版本追溯，
而这些都是已经建成的能力。

浏览器写不了任意本地路径，落盘有两条路：
File System Access API（Chromium，授权一次，标签页关了就停）
或轻量本地同步器（更稳，也是将来做桌面客户端的路）。**同步器方案待定。**

**代价**：本地目录可能与对象存储不一致（用户手动删了文件）。
不做双向同步，也不以本地文件为准恢复——不一致时以对象存储重新落一份。

## ADR-023 审查模式三档，默认半自动

**日期**：2026-08-18

**决定**：出图/出视频阶段声明 `review` 策略，用户在项目级选三档之一：

| 模式 | 判定者 | 不合格时 |
|---|---|---|
| `manual` | 用户 | 用户改提示词重生 |
| `assisted` | AI 筛 + 用户裁 | 只把 AI 判不合格的推给用户 |
| `auto` | AI 打分 vs 阈值 | 自动重试，超 `max_attempts` 则停下问人 |

允许 `auto` 的阶段**必须**声明 `metric` 与 `threshold_key`。
**阈值只写键名，数值进库**——理由同 ADR-014：
相似度阈值仍在标定中，写死在会被分发的 YAML 里等于把待定数字冻起来。

**原因**：`consistency/metrics.py` 的实测数据已经证明单一全局阈值必然误判——
构图差异对整图 embedding 的影响和身份差异是同一个量级，
0.75 会把所有远景和特写都判成"角色崩了"。中间地带交人工是有数据支撑的默认值，
不是保守。

场景概念图没有基准图可比，现阶段 `allow_auto: false`；
TTS 没有可计算的音质指标，同样不开放全自动——
那只会变成"没人听过就发出去了"。

**代价**：半自动仍需用户参与，达不到"睡一觉起来片子好了"。
等人工判定数据积累够，用它反过来标定阈值，再逐阶段放开 `auto`。

## ADR-024 模型选择在项目级覆盖，Agent 仍不选模型

**日期**：2026-08-18

**决定**：用户可在项目级按 **capability** 覆盖模型
（`project.model_preference`），Gateway 解析时优先读覆盖。
Skill 用 `model_policy.user_selectable` 声明哪些能力可由用户改。

**ADR-002 不变**：Agent 仍然只声明 capability，不指定具体模型。
覆盖发生在项目层，不在 Agent 层。

**原因**：用户要"便宜点"或"好看点"是合理诉求，
但让 Agent spec 写死模型会让每次上游调价都要改 spec。

**两条硬约束**：

1. **换模型必须重算 Credits 预估**，走 `model_pricing` 表，不沿用旧数字
2. **部分 role 禁用推理模型**（`model_policy.no_reasoning_roles`）。
   `deepseek-v4-*` 的思考 token 计入输出预算，用在分类和结构化抽取上
   会返回**空内容且不报错**——已踩过两次

**代价**：暴露给普通用户的应是**档位**（经济/标准/高质）而非模型 ID。
档位到模型的映射是另一张表，尚未建。

## ADR-025 用户自带 Key（BYOK）走大幅折扣，不是免费也不是全价 ★

**日期**：2026-08-18

**背景**：用户要求"在配置页面直接配自己的模型 Key"。这会直接冲击
`19_UnitEconomics.md` 的毛利模型——那份文档从头到尾假设的是
"平台用自己的 Key 转发调用、赚上游成本与售价的差"。用户自带 Key 时，
平台不再承担 `provider_cost`，但**没有停止承担别的成本**：
存储、CDN、审核、系统故障重跑计提——这些是 `19_UnitEconomics.md` 1.5 节
"隐性成本"，跟调用哪个 Key 无关，BYOK 不能让这部分也变成免费。

**决定**：

1. 项目/用户配置了某个 capability 的自有 Key 时，该 capability 的
   Credits 预估**跳过 `model_pricing` 里的 `provider_cost` 加价部分**，
   只按 `19_UnitEconomics.md` 1.5 节的隐性成本档位收一笔小额 Credits
   （具体数值走 `pricing_rules`，不写死——理由同 ADR-014）。
   不是完全免费：完全免费等于邀请用户拿自己的免费/低价 Key
   无限占用平台存储和计算，免费额度设计（`19_UnitEconomics.md` 第 5 节）
   会被绕过。
2. **用户资产库的 1GB 配额（见项目页面另附）天然是第二道防线**：
   即使 Credits 侧几乎不花钱，存储侧的物理上限仍然卡着，
   不需要为 BYOK 单独再造一套滥用检测。
3. Key 走 `_encrypted` 字段（应用层 AES-GCM，`09_Database.md` §附录
   已有约定的加密字段命名规范），只在 Gateway 解密后用于当次请求，
   不回显给前端、不进日志、不进 `input_json`——这条是 CLAUDE.md
   "密钥不进代码、不进日志、不进 input_json" 的直接推论，没有新增例外。
4. 用户可为哪些 capability 配自己的 Key，由 Skill 的
   `model_policy.user_selectable` 决定（复用 ADR-024 已有的开关，
   不新开一套声明）。

**原因**：全价计费会让"自带 Key"这个功能对用户毫无吸引力
（花钱买了自己的 Key 又要付平台全价，等于白花钱）；完全免费会让
`19_UnitEconomics.md` 的免费额度设计形同虚设，且给了刷子低成本
占用平台资源的空子。折扣但不免费，两头都保。

**代价**：`billing/pricing.py` 的估价公式要多一个分支
（"这个 capability 是不是走了用户自己的 Key"），实现前需要先给
`model_pricing`/`pricing_rules` 加对应的折扣系数键名。

## ADR-026 Skill 上传本轮只做到"能传、能选"，不接运行时

**日期**：2026-08-18

**背景**：`12_MVP_Roadmap.md` 把"用户自定义 Skill"排在 **M5（Skill 生态）**，
比当前所在的 M2 晚三个里程碑；`2026-08-18 进度与开发计划.md` 也明确写
"Skill 运行时之前不要做，阶段图还在频繁变，固化太早只会白改两遍"。
用户这次要求提前做"上传 Skill、切换 Skill"这个面向终端用户的功能。

**决定**：本轮只做到**上传、校验、项目内选择**，不做**运行时接线**：

- 用户可以上传 Skill YAML（走 `04_SkillSpec.md` §7 已定的白名单校验：
  处理器白名单、导出路径白名单、门白名单、能力白名单、重试次数上限——
  这套校验本来就是为"不可信输入"设计的，本轮直接复用，不新增豁免）
- 项目里可以选择"用哪个 Skill"，选择被存下来
- **选了非默认 Skill 时，生产流程实际上仍然走 `orchestrator._NEXT`
  硬编码的阶段图**，跟 ADR-020 记录的现状一致——选择目前不生效，
  界面要如实标注（比如"预览"或"即将支持"），不能假装已经生效

**原因**：真正让"切换 Skill"生效，需要把 `orchestrator._NEXT` 从硬编码
搬到读 Skill 声明驱动，这项工作量与 M2 本身（TTS/时间线/ffmpeg）相当，
而 M2 阶段图现在还会因为出片链路继续变——现在接线等于要为同一张图改
两遍。上传与选择的 UI/数据层可以先做且不受这个影响：Skill 记录、
校验逻辑、选择状态都是稳定的，不会因为阶段图变化而返工。

**代价**：用户能上传 Skill，但上传了也暂时看不到效果——这是本轮
刻意留下的半成品，验收标准里必须包含"UI 明确告知运行时未接线"，
不能做成一个看起来能用、实际不生效的功能。运行时接线本身留到
阶段图随 M2 稳定之后，作为独立一轮做，到时候再补一条 ADR。

## ADR-027 自带 Key 的调用与熔断按 org 独立，且不回落平台 Key ★

**日期**：2026-08-19

**背景**：ADR-025 把 BYOK 的**计费**做完了——配了自有 Key 的能力按隐性成本
档位收费，跳过 `model_pricing` 的 provider_cost 加价。但 Gateway 的
`_build()` 仍然是进程启动时读一次环境变量、建一张平台 Key 的路由表，
**实际调用用的还是平台的 Key**。于是每一次 BYOK 生成都是：用户按折扣价付款、
平台按全价掏钱买上游。差额没有任何告警，账上只体现为毛利莫名其妙地掉。

**决定**：

1. Key 的解析从"进程启动时读一次环境变量"改成"每次调用按
   `org_id + capability` 现查"。查到就用那把（`KeySource.ORG`），
   查不到落回平台路由表（`KeySource.PLATFORM`，行为与本 ADR 之前完全一致）。
   **不缓存**：缓存等于"删了 Key 还在用"，而删 Key 的人多半正是因为它泄露了。
   代价是每次生成多一次带索引的单行查询加一次 AES-GCM 解密，
   相对一次几秒到几十秒的生成可以忽略。
2. **熔断按账号分作用域**：平台档一个，每个自带 Key 的 org 各一个。
   合起来算两个方向都错——一个用户的 Key 被上游封了会把整家 Provider
   熔断掉、把所有用平台 Key 的人一起降级；反过来平台账号出问题时
   拦住用自己 Key 的用户同样没道理，那是另一个账号。
3. **BYOK 不跨 Provider failover，尤其不回落平台 Key**。用户只配了一家，
   "轮换到另一家"这个选项不存在；回落平台 Key 则是把第 1 条要堵的洞
   原样搬到了失败路径上。同一把 Key 换模型仍然允许（同账号同价），
   但账号级失败（鉴权、欠费）连模型都不换。
4. 自有 Key 失败时报 `provider.byok.rejected`，而不是把上游的
   `provider.account.insufficient` 原样透出去：后者的用户文案是
   "服务暂时不可用，请稍后重试"，而这种情况等下去永远不会好，
   只有用户自己能修。上游的具体分类留在 `detail.upstream_code`，
   沿用 ADR-025"测试连接"那套，不另造一份。透出前必须过一遍脱敏——
   上游 401 常把收到的 Key 原样贴回来，而这条 message 会被写进
   `agent_runs.error_detail`。
5. 适配器每次调用记一条 `provider.call` 信号，带 `key_source` 枚举
   （**只有枚举，没有 Key、没有尾号、没有密文**）。它是唯一能证明
   "确实用了自有 Key"的东西：计费查的是库里有没有那一行，调用用的是解出来的
   那把 Key，两者完全可能背离——本 ADR 之前正是背离状态。

**原因**：第 1 条是止血，后面四条都是它的直接推论。真正的判断题只有
第 3 条：回落平台看起来对用户更友好（他的 Key 坏了也照样出片），
但那正是重新打开财务漏洞的做法，而且把"你的 Key 坏了"这个只有用户能修的
问题永久藏了起来。

**代价**：

- 每次生成多一次 DB 查询 + 一次解密。
- 用户自己的 Key 坏掉时生成会失败，而不是静默降级——这是刻意的，
  但要求设置页的"测试连接"足够好用，否则用户会卡在"为什么突然不能生成了"。
- 熔断作用域按 org 分之后，Redis 里的 `cb:provider:*` 键数量随自带 Key
  的 org 数增长。键本身带 TTL（失败窗口的 4 倍），不会无限堆积。

## ADR-028 资产库分类用独立关联表；参考描述生成角色复用同一个 Agent，另存一张表 ★

**日期**：2026-08-19

**背景**：借鉴同类产品（AgentCine）的资产库做两件事：用户能自建文件夹给
资产归类；能直接写一段角色描述就得到一份正式角色档案，不必先建项目、
先传小说、先跑完路由和剧本。第二件事撞上了一个既有假设——**角色档案跟着
项目走**。现有实现里它们存在 `agent_runs.output_json`，而
`agent_runs.project_id` 是 NOT NULL，资产库、项目详情、编排器全都按项目查它。
（它的多套外观变体 appearances 本轮不做：那依赖真实出图，而出图还没接进
生产链路，等 M2 之后再说。）

**决定**：

1. **归类关系走独立的 `asset_folder_items`，不给任何现有表加 `folder_id` 列。**
   要归类的四种东西里，角色/场景档案存在 agent 模块的表上——asset 模块不能
   往别的模块的表上加列（ADR-009）。一张关联表让四种东西走同一套归类逻辑，
   且不动任何现有表结构。一个条目同时只属于一个文件夹：多重归类的收益
   远小于"这份档案到底在哪"的困惑。关系行硬删（它没有审计价值），
   文件夹软删。
2. **文件夹属于用户，不属于项目。** 资产库本身就是跨项目的（配额按账号算），
   分类挂到项目上会让"配角参考"在每个项目里各存一份。
3. **独立角色档案另起 `character_entries`，不把 `agent_runs.project_id` 改成可空。**
   松一条被四处依赖的 NOT NULL 约束，等于让所有"按项目查档案"的代码都要
   重新考虑 NULL 的语义；而新加一张表谁都不影响。代价是"角色档案"在库里
   有两个存处，靠 output 是同一个 `CharacterSheets` schema 把它们钉在一起。
4. **复用 `visual.character.v1`，不新增"简易版角色 Agent"。** 输入形态不同
   （参考描述 vs 剧本），要产出的东西完全一样。两份相似的角色提示词一定会
   分叉——改了一处忘了另一处，两条入口生成的角色就不是一个标准，
   而这正是 ADR-020 拆三份提示词时要避免的失败模式（拆开的是**职责不同**的
   提示词，不是同一职责的两个副本）。输入形态的差异由 `system_suffix` 抹平，
   和聊天修订用的是同一个机制。
5. **`runner` 拆出 `complete_structured`**：提示词合成 + 输出契约 + schema
   校验 + 重试，不碰数据库；`run_agent` 在它外面套一层落 `agent_runs` /
   `agent_steps`。不挂项目的调用只用内核那一半，把过程存进自己的表。
   两条路径共用同一套约束，spec 的四重限制一条都没被绕开。
6. **同步 Agent 调用照常走 Credits 预扣/结算**，预扣额取 spec 的
   `budget_credits`（它本来就是"单次运行成本上限"），结算按实际输出 token
   查 `model_pricing`，差额退回。流水的 `ref_type` 记 `character_entry`，
   不写 `task`——指向一个不存在的 task 会让对账查不下去。

**原因**：第 1、3 条是同一个判断的两面——**为一个新入口去松既有约束，
风险远大于多一张表**。第 4、5 条是同一个判断的两面——**共用提示词，
不共用存储**。

**代价**：

- 归类关系与被归类的东西之间没有外键（跨模块不能加），删掉一个资产时
  关系行会变成孤儿。目前只在删角色档案时顺手清理；孤儿行不影响展示
  （列表是从实体侧查出来再打标的），但需要一个定期清理任务，记在 M2。
- 文件夹视图不分页。容量由 `MAX_FOLDER_ITEMS` 封顶；先分页再按归类过滤
  会得到一页空结果，那比不分页糟得多。
- 生成的独立角色档案**还不能被项目的生产流程消费**——那需要设计外部角色
  档案怎么进 `current_state_json`，超出本轮范围。前端照 ADR-026 的做法
  明确标注"未接生产流程"，不做一个看起来能用的按钮。
- 结算金额向上取整（不足 1 Credit 按 1 收）。向下取整会让一次约 600 个
  输出 token 的调用收 0（2026-08-19 真机验证发现），那是系统性漏收。

## ADR-029 字段级编辑走 JSON Patch 打在 `current_state_json` 上，变更历史按批可撤销 ★

**日期**：2026-08-28

**背景**：对照 ReelBench 的评估（`_research/reelbench_arch_review.md` §1.3）指出一处
**根本性缺口**：我方没有任何"改一个字段"的写路径。角色/场景/分镜的正文全在
`projects.current_state_json[stage]` 这一块 JSONB 里，唯一的修改方式是
`POST /projects/{id}/revise`——写一句自然语言，让同一个 Agent 把整块产出重写一遍。
那条路慢、每次是一次真实 LLM 调用要走 Credits 预扣结算、而且模型可能顺手改坏
别的字段（`agent/revise.py` 里 `diff_fields` 存在的全部理由就是抓这件事）。

这不是"缺一个便利功能"。**不做这条路，ReelBench 式的表格/卡片编辑界面就只能是
一个"看起来能编辑、点了却在调模型"的假界面**——而那种界面比没有更糟。
同时缺的还有变更历史：`conversation_messages.changed_fields` 是
`["characters[lin_shu]"]` 这样给人读的字符串，不含新旧值，回放不了也撤销不了。

**决定**：

1. **JSON Patch 打在 blob 上，不做实体化。** `PATCH /projects/{id}/outputs/{role}`，
   body 是一组 `(JSON Pointer, 新值)`。评估文档列的三条路线里选 B：
   全实体化（角色/场景/道具各建表）最干净但迁移面积最大，且要重写 `revise`
   那条"整块喂回模型"的路；只做 revise 不可接受。**B 不挑战 ADR-008**——
   唯一权威仍是 `current_state_json`，只是给它开了一条确定性的写路径。
2. **校验复用 `agents/schemas.py` 的 Pydantic schema，整块重新校验，不新写一套
   字段规则。** 另写一套必然与 schema 漂移，而漂移的方向永远是"校验比 schema 松"。
   整块校验而不是只校验被改的字段：单字段合法但整块非法是常态（`personality`
   是个合法的字符串数组，但它有 `min_length=1`）。role → schema 从 Agent spec 的
   `output_schema` 反查，不另建一张映射表。
3. **只替换已存在的路径。** 不新建键、不追加数组元素（不支持 RFC 6901 的 `-`）。
   新建键必然被 `extra="forbid"` 顶回来；而"追加"看着无害，却让撤销从
   "写回旧值"变成"删掉一个元素"，是另一套语义和另一套并发风险。要加人物就重跑 Agent。
4. **路径里和 value 里任何以 `_` 开头的键一律拒绝**，另加 `constructor` /
   `prototype` 黑名单。我方产出里不存在这种键所以不误伤；它挡掉的是原型污染载荷——
   后端是 Python 看着无所谓，但这份 JSON 会原样进前端，在那边 `obj[key] = v`
   就是真的原型污染。
5. **一次 UI 操作 = 一个 batch = 一个事务。** 改产出、记 `content_revisions`、
   同步一致性投影三件事同生共死。批不单独建表：一批的元信息在每行上都是同一个值，
   冗余几十字节换掉一张表和一次 join。
6. **写路径必须同步角色/场景一致性投影，且失败要整批回滚。** 这一点与编排器里的
   `_sync_consistency` **刻意不同**：那边吞掉异常是因为它前面刚花过一次真实的模型
   调用，为一次写库失败让用户重跑等于再花一次钱；这边一分钱没花，重试免费，
   所以宁可整批失败也不留下"产出改了、投影还是旧的"——那正是用户眼里
   "改了发色但出图还是黑发"的成因（评估文档 §5.1 风险 1）。
7. **撤销是反向重放同一条写路径，不是 DELETE。** 撤销本身也进变更历史，
   因此可审计、可再被撤销（相当于重做），且不需要第二套写代码。
8. **同一批只有当每个字段的当前值仍等于当时写下的 `new_value` 才可撤，否则整批 409。**
   否则退回去就是把后来那次改动无声地抹掉，用户会看到一个自己从没做过的值
   且找不到是谁干的。**不做部分撤销**：撤一半出来的是一个既不是改前也不是改后的
   第三种状态，没有人要过它。
9. **这条路径一分钱不花。** 不建 Task、不建 AgentRun、不调模型、不预扣也不结算，
   `billing` 在它的调用链上一行都不执行。测试里每个用例都在断言反面
   （无 Task、无 AgentRun、无 Ledger 流水、余额不动），因为唯一的风险就是
   哪天有人把它接回 `create_task`。

**原因**：第 1、2 条是同一个判断的两面——**复用既有的真相源和既有的校验，
换取零迁移和零现有路径改动**。`revise`、`variables_for`、两个一致性同步钩子
一条都没被动过。第 7、8 条也是同一个判断的两面——**撤销不是特权操作，
它和用户手动改字段走完全一样的校验、记账和投影同步**，所以它不需要
（也不允许）绕过任何一条规则。

**代价**：

- **`revise` 还没有写进 `content_revisions`**（`SOURCES` 里预留了 `agent_revise`）。
  所以变更历史现在只有人工改的那一半，模型改的那一半仍然只在
  `conversation_messages` 里以字符串形式存在。后果是评估文档提到的
  "把完整修改史复制给 agent"这个用法暂时喂不全。接它要动一条已经在跑的
  花钱链路，本轮不碰。
- **blob 里没有实体主键**，所以 `field_path` 里的数组下标（`/characters/2/hair`）
  是位置而不是身份。重跑一次 Agent 让数组顺序变了，历史里的旧路径就指向别人了。
  当前靠"撤销必须先匹配 `new_value`"挡住这种误伤——匹配不上就 409，不会写错人。
  真正的解法是评估文档 §5.1 风险 3 说的持久化显示码，那要先定 ref 与显示码的
  关系，本轮没定。
- **历史分页游标是单值 `created_at`**，与项目列表的写法一致。同一微秒内落两批会
  漏一批。批的时间戳取的是 PostgreSQL 的事务时间，人手速度下不会撞；
  真要严谨得上复合游标，本轮按既有约定走。
- **前端尚未接线**。本轮只有后端契约与测试，界面上还没有可编辑的表格。

## ADR-030 `/freeflow` 替换主线四栏工作台，旧壳只留 `/login` ★

**日期**：2026-09-02

**背景**：REQ-000（要不要用"分支 B·自由工作流"替换主线四栏工作台）从 8 月 25 日
悬到今天。期间 `/freeflow` 已经长成一套完整的路由级信息架构（项目大厅、七个项目页、
全局导航），而旧 `(app)` 工作台仍然是审批、返工、内容修订的唯一入口。两套壳并存的
代价在 `project_docs/modules/11_WEB_WORKBENCH.md` 里列过：重复实现、设计不一致、
新 Worker 不知道该改哪边。`_research/reelbench_arch_review.md` §3 建议"先双模式、
设终止条件、最终合流"，终止条件一直没人写。

**决定**：

1. **`/freeflow` 是唯一正式工作台。** `(app)` 下只保留 `/login`，其余路由全部删除，
   `/dashboard` 重定向到 `/freeflow`。
2. **删旧壳的唯一前置条件**：freeflow 能独立跑完
   「新建项目 → 剧本确认 → 分镜确认 → 出图」，中途不跳回 `/projects/{id}`。
   达到即删，**不追求功能对齐**。旧壳里 freeflow 没有的东西（对话流、输出抽屉）
   按需迁移，不作为删除的门槛。
3. 迁移方式是**把旧壳的真实能力迁入 freeflow 的组件层**，不是复制页面。
   审批门、`revise`、内容修订、输出版本、素材上传这五条按 `11_WEB_WORKBENCH.md`
   的清单逐条迁。
4. freeflow 里的空壳一并清理：`members`、`servers`、`templates` 摘出导航并删路由；
   `mock-data.ts` 的主链路引用删除、文件随 Canvas 搁置；悬浮 AI 助手连路由摘掉
   （它只返回本地预设回复）。`/freeflow/skills` 这个占位路由也删——真正的技能清单
   在资产库的「技能」chip 里，那里保留并继续诚实标注"运行时未接线"（ADR-026）；
   Skill 上传入口迁到同一处。
5. 节点画布（Canvas）**搁置**：路由从导航隐藏，代码保留，不接后端。
   它是分支 B 设计包的核心验证物，删了以后再要就得重做；但主导航上不许出现
   一个"运行"按钮不会提交任务的页面。

**原因**：两套壳每并存一周就多一周的重复实现，而且重复的那份永远是假的
（freeflow 的故事编辑存在组件本地、任务页读 `agent_runs`）。定一条可验证的
前置条件比定一个日期可靠——日期到了功能没到，只会再延一次。

**代价**：

- 旧壳的对话流（每步一张结果卡片 + 抽屉）是 S12 花过力气的交互，freeflow
  的产物优先架构里没有对等物。**接受**：ReelBench 评审的结论就是"产物优先"，
  对话流退化为项目概览里的运行记录。
- 设计稿 `design-system/aigc-studio/MASTER.md` §5 的四栏版式作废，需要一次
  设计系统文档同步。

## ADR-031 用户直接选模型；默认值分三层；供应商走固定目录 ★

**日期**：2026-09-02

**Supersedes**：ADR-024"代价"一段（"暴露给普通用户的应是档位而非模型 ID，
档位到模型的映射是另一张表"）。ADR-024 的决定本身（项目级按 capability 覆盖、
Agent 仍不选模型）和两条硬约束（换模型必重算 Credits 预估；部分 role 禁用推理
模型）**继续有效**。

**背景**：负责人要求用户能在设置里添加供应商、选全局默认的视频/文本/TTS/图像
模型，并且**在每次生成前自己选**，用来对比不同模型的效果。这与 ADR-024 设想的
"用户只看到经济/标准/高质三档"直接冲突。冲突的根源是用户画像变了：ADR-024
面向"要便宜点或好看点"的普通用户，现在面向要对比 Seedance 和万相谁更好的创作者。

**决定**：

1. **用户看到的是模型，不是档位。** 每个能力下列出当前用户可选的模型
   （显示名 + 供应商 + 单价折算的 Credits 估算），档位映射表不建。
2. **能力维度四个**：`text_generation` / `image_generation` / `video_generation` / `tts`。
   图像编辑（图生图）不在本轮，加能力时另提 ADR。
3. **默认值三层，解析顺序固定**：
   生成前临时选择 > 项目覆盖（`projects.model_preference`，ADR-024 已有）> 组织默认。
   临时选择**只对本次生效，不回写**任何默认。组织默认的存储是新表，由
   `05_MODEL_GATEWAY.md` 定字段。
4. **生成前选择必须是界面上的模型选择按钮**，不能靠用户在对话里说"用 Seedance"。
   按钮的数据来源是一个"本能力下可选模型 + 各自 Credits 估算"的接口，
   估算走 `model_pricing`（ADR-024 硬约束 1）。
5. **供应商来源是固定目录**：每家由代码内 adapter 声明能力、模型列表、定价键名、
   以及视频能力的"单段最大时长"（ADR-032 要用）。用户"添加供应商"= 给目录里的
   某家填 Key（BYOK，ADR-025 折扣）。**例外：文本能力允许一个 OpenAI 兼容自定义
   端点。** 视频和 TTS 不允许自定义端点——各家请求形状差异太大，"填个 URL 就能用"
   做不到，做了就是假入口。
6. Key 两条路并存：默认平台 Key 全价扣 Credits；用户自带 Key 按 ADR-025 打折。
   不强制外部用户先去申请五家 Key。
7. `gateway._resolve` 现有行为**保留**：偏好只重排候选顺序，选中模型失败仍自动
   failover 到同能力下一个。用户明确选了 A 却被静默换成 B 会破坏"对比效果"这个
   用例，所以 **failover 发生时必须在任务结果里标明实际使用的模型**，前端要显示。

**原因**：第 1 条是用户画像变化的直接后果。第 5 条的例外只给文本，是因为
OpenAI 兼容协议在文本上是事实标准，在视频和 TTS 上不存在这种标准。第 7 条
保留 failover 是因为 Gateway 的熔断和 failover 是 S6 最有价值的部分，为了
"所见即所用"扔掉它会让单家故障变成全站故障；折中是**用了谁必须说**。

**代价**：

- 模型列表暴露给用户后，上游下线一个模型会直接变成用户可见的错误。
  目录里每个模型要有 `available` 状态，下线的不出现在按钮里但历史记录仍能显示。
- 三层默认让"这次到底用了哪个模型"的溯源变复杂。每个生成任务的 `input_json`
  必须记下解析出的模型和它来自哪一层。

## ADR-032 第一条成片是"逐镜 MP4"，镜内按模型单段上限切段，段上限是分镜阶段的输入 ★

**日期**：2026-09-02

**背景**：`12_MVP_Roadmap.md` 和 `19_UnitEconomics.md` 一直把 M2 定义为
"TTS → 音频优先时间线 → ffmpeg 合成 → 第一条完整成片"。负责人 2026-09-02 把终点
改小：**每个镜头一条带配音的 MP4**，用户拿到之后自己决定在平台上拼（后续版本）
还是去剪映。字幕、BGM、转场、整集时间线都不在第一条成片里。

同时定了视频的最小单元。不同模型单段能生成的时长差异很大：万相约 5 秒，
Seedance 15 秒以上。一个 12 秒的镜头，用万相要切三段，用 Seedance 一段就够。

**决定**：

1. **M2 的验收物是逐镜 MP4**：视频 + 该镜台词的 TTS 混音后的单文件，可单镜下载、
   可批量下载全部镜头。没有字幕、BGM、转场、整集合成、剪映导出。
2. **视频按镜生成。** 镜的时长由该镜台词的 TTS 真实时长推导（音频优先，
   `17_ConsistencyEngine.md` 和 `19_UnitEconomics.md` 早就定了这条），
   再受镜的最小/最大时长约束。
3. **镜内切段。** 每个视频模型在 adapter 里声明"单段最大时长"（ADR-031 第 5 条）。
   镜时长超过上限时切成 N 段，每段一次图生视频调用，段拼成镜。
   Seedance 这类长段模型下 N 通常等于 1。
4. **视频模型的单段上限是分镜阶段的输入。** 分镜生成时就要拿到项目当前视频模型
   （按 ADR-031 三层解析）的上限，据此定每镜时长和段数。出图之后再算段数会让
   分镜表上的时长和实际生成的对不上。换视频模型后段数会变，属于"上游变更"，
   按候选版本规则（ADR-033）标记过期而不是自动重跑。
5. **段与段之间的首帧衔接：沿用上一段末帧**（ffmpeg 抽末帧作为下一段的首帧图；
   2026-09-02 晚定，三方案代价见 `12_MEDIA_TIMELINE_EXPORT.md` §7）。模型不支持时
   降级为共用首帧；首尾帧模式等 Seedance 接入后按模型能力开关。镜内段串行生成，
   段数通常 1~3，串行代价可接受。
6. **合成只做一件事**：ffmpeg 把段拼成镜、把配音混进去。Render Spec 是结构化
   白名单参数，禁止 Agent 生成 shell 命令（这条 `12_MEDIA_TIMELINE_EXPORT.md`
   旧版已写，保留）。
7. 视频和 TTS 的计费走同一套 reserve/settle/release，估算按 `model_pricing`，
   不写常量。

**原因**：把终点从"整集成片"改成"逐镜 MP4"砍掉的正是 M2 里最不确定的部分
（时间线数据模型、多轨混音、字幕烧录），保留的是最能验证核心假设的部分
（一致性、i2v 质量、TTS 对齐）。第 4 条是因为"分镜时长"和"视频能生成多长"
是同一个数的两面，分开算必然不一致。

**代价**：

- `19_UnitEconomics.md` 的盈亏平衡按"每天 16 部成片"算，"部"的定义现在是
  逐镜 MP4 的集合而不是一条片。成本模型里每部的镜数和段数要重估，
  **本轮不重估**，等第一批真实数据。
- 用户拿到几十个 MP4 要自己拼，第一批用户会抱怨。接受，这是负责人的取舍。

## ADR-033 每镜的图和视频都是"多候选 + 恰好一个当前版"，下游记录消费的版本 ★

**日期**：2026-09-02

**背景**：ADR-031 让用户在生成前换模型对比效果，那每次生成的结果都要留下来并排看。
现状：`GET /projects/{id}/images` 合并 `tasks` 里的生成记录和档案上钉的基准图，
按时间倒序，前端"取第一条就是当前版"（S14）。这个约定在"生成三张挑一张"下不成立。
S14 已经做了一半：钉基准图不删旧资产、不递增 version。

**决定**：

1. 每镜的首帧图、每段的视频、每镜的配音，都是**候选集合 + 恰好一个当前版**。
   每次生成新增一个候选；用户切换当前版不删旧候选；旧候选可以被手动删除但
   不会被自动清理。
2. `GET /projects/{id}/images` 的"取第一条就是当前版"约定**作废**，改为每条带
   `is_current`。视频、配音的列表接口同一形状。
3. **下游只消费当前版，并记录消费时用的是哪一版。** 配音消费分镜台词、视频消费
   首帧图、MP4 合成消费段视频和配音——每一步都在自己的记录里写下上游候选的 id。
   上游切换当前版后，下游记录里的 id 与新当前版不一致，就是"过期"。
4. **过期只标记不传播。** 界面上显示"上游已换，待重出 / 保留当前版"两个动作
   （ReelBench 的做法），用户决定。自动计算影响集并重跑是 P1。
5. **候选按业务各建表**（首帧图候选、配音候选、段视频候选），`assets` 只存文件与血缘，
   不加"变体组 / 当前版"字段（2026-09-02 晚定）。理由：`assets` 是通用文件表，
   "当前版"的语义按镜 / 段 / 配音各不相同，塞进去会长出三套业务字段。
   `07_ASSET_LIBRARY.md` 与 `12_MEDIA_TIMELINE_EXPORT.md` 按此对齐。

**原因**：第 3 条是整个"过期"机制的地基——没有"消费了哪一版"的记录，
就只能靠时间戳猜，而时间戳在"重新生成但没切换当前版"时会误判。
第 4 条不做自动传播是因为影响集计算要先有依赖图，那是 P1 的事。

**代价**：

- 候选不自动清理，对象存储会涨。定期清理策略是运维事项，`14_PLATFORM_OPERATIONS.md`
  记一条。
- 前端所有"当前图"的取法要改，S11/S14 的 `RenderSlot` 和右栏角色卡都要动。

## ADR-034 视频时长是**离散档位集合**，不是"单段最大时长"；镜内切段降级为待定 ★

**日期**：2026-09-05
**Supersedes**：ADR-032 第 3 条、第 4 条（第 5 条随之失效，见下），以及
`12_MEDIA_TIMELINE_EXPORT.md` §9.1 的段数算法。ADR-032 的其余各条（逐镜 MP4 是
M2 验收物、音频优先、合成只做拼接与混音、计费走同一套）全部保留。

**背景**：ADR-032 第 3 条把每个视频模型的能力建模成一个标量——"单段最大时长"，
镜时长超过它就切 N 段平均分配。2026-09-05 逐条核对同行实现（`_research/ArcReel-reference/`）
后确认，**这个模型在真实供应商上不成立**：

- 时长是**非空离散集合**，不是区间。可灵全系只接受 `[5, 10]`；MiniMax Hailuo
  只接受 `[6]`（集合里只有一个值）；Veo 3.1 是 `[4, 6, 8]`。
- 我们的算法对一个 13 秒的镜会算出"3 段 × 4.34 秒"。在可灵上三段全是非法值，
  在 Hailuo 上同样三段全非法。**这不是边角情况，是主流程第一次真实调用就会撞上。**
- 档位还会被分辨率和"带不带参考图"二次收窄：Veo 3.1 在 720p 可选 4/6/8，
  1080p 只剩 8；一旦带参考图，任何分辨率都只剩 8。一个标量表达不了这件事。
- 同行为此写过一条 ADR，起因是真实事故：内部把 6 秒静默映射成 8 秒、加上
  `or [4,6,8]` 这类隐性兜底，导致"用户选 6 秒却被改成 8 秒，再被对端拒为非法"。

同时，**镜内切段这件事本身可能整体不必要**。ADR-032 写"万相约 5 秒"，那是
wan2.1/2.2 的数据。wan2.7 是 2–15 秒任意，wan3.0 是 2–30 秒任意，Seedance 是
4–15 秒任意。在我们主用的这几个模型上，一个 12 秒的镜 N 恒等于 1。而为切段
付出的代价是：4 张新表、ffmpeg 抽末帧、段串行、失败放大、段间画面漂移累积，
以及"切换第 N 段的当前版会让第 N+1 段的首帧失效，进而让整条后续链全部过期"。
同行没有任何镜内切段的概念，他们的答案是取档 + 超上限就要求用户改内容，零新增表。

**决定**：

1. **模型能力声明改为离散档位集合。** `VideoModelSpec.max_segment_ms: int` 作废，
   改为 `supported_durations: tuple[int, ...]`（**非空**）。解析不到就抛异常，
   **禁止任何隐性兜底**——不许写 `or [4, 6, 8]` 这类默认值，不许把一个不在集合里的
   值静默映射到邻近档位。这两种写法正是同行那次事故的根因。
2. **补上时长的联动约束**：`duration_resolution_constraints`（按分辨率收窄的档位）
   与 `reference_image_durations`（带参考图时可用的档位）。声明不出来的模型不接。
3. **取档语义是"容量"不是"裁剪"**：取大于等于基准时长的最小合法档位，成片不做裁剪。
   `resolve_duration_slot(total_seconds, supported) -> DurationSlot(seconds, adjustment)`，
   `adjustment ∈ {exact, up, down}`。
4. **超过最大档位不切段，而是阻断并要求用户改内容**（拆镜，或换一个支持更长时长的
   模型）。**镜内切段从"已决定"降级为"待定"**：等出现一个既是主力、单段上限又
   确实短于常见镜长的模型时再重新评估。在此之前按 N=1 实现，
   `shot_segments` / `segment_videos` 两张表**不建**。
   ADR-032 第 5 条（段间沿用上一段末帧）**随之失效**——没有段就没有段间衔接。
   镜与镜之间的连贯性改在图像层解决，见 ADR-035。
5. **换档必须用户确认。** 取档结果与用户看到的时长不一致时，接口返回 422 并带上
   新旧时长与新旧价格，由用户确认后再生成。理由：换档改价，而 ADR-024 硬约束 1
   要求"换模型必须重算 Credits 预估"——这一条就是那条约束在时长维度上的落地形态。
6. **生成完成后用 ffprobe 复核实际时长。** 上游返回的时长不可信（05 文档 §4.3 早就
   记了"要 5 秒给 4.8 秒"）。实际时长短于配音时长时任务判失败，不进当前版，
   错误码 `media.video_shorter_than_audio`（新增）。测不出时长同样判失败，不静默放行。
7. **音频优先的表述收紧**：配音时长是取档的**下限**，不是"决定时长"。
   `duration_input = max(计划时长, 配音真实时长)`，再取档。且**过期的配音不参与定时长**。

**原因**：第 1 条和第 4 条是同一件事的两面——我们此前把"模型能生成多长"理解成
一个连续量，于是自然推出"超了就切"。一旦承认它是离散集合，"切段"就失去了地基：
切出来的每一段仍然要落在集合里，而平均分配几乎必然落不进去。与其做一套复杂的
"按档位组合凑总时长"，不如先承认在主力模型上 N=1，把那 4 张表和末帧衔接的全部
复杂度推迟到真正需要的那天。

第 6 条是我们此前完全没有的一道防线：视频是付费且不可撤销的，"上游说它给了 8 秒"
和"文件里真有 8 秒"是两件事，而后者才决定用户听到的配音会不会被截断。

**代价**：

- `05_MODEL_GATEWAY.md` §4.4 的 `VideoModelSpec`、`12_MEDIA_TIMELINE_EXPORT.md`
  §5 的表设计与 §9.1 的算法都要改。改在没有任何视频代码之前，代价是文档级的。
- 用户会遇到"这一镜太长，请拆镜"这种阻断。这是有意的：另一条路是替他做主，
  把 13 秒静默变成 10 秒，那意味着配音被截掉 3 秒且不告诉他。
- 分镜阶段仍然需要拿到当前视频模型的档位集合（ADR-032 第 4 条的合理内核保留），
  只是消费的是集合而不是标量。

**验证前提（未做，需要花钱）**：本 ADR 的档位数据全部来自同行仓库的二手整理，
其调研截止日期是 2026-05-27，可能已过时。落地前必须用我们自己的 Key 对
wan2.7 实调一次，确认它是否真的接受 2–15 秒任意值。这一次调用同时能验证
"镜内切段要不要做"这个判断。**在负责人批准花这笔钱之前，本 ADR 的第 4 条按
"暂按 N=1 实现，但不删除重新评估的余地"执行。**

## ADR-035 候选版本收成一张表；"过期"改用内容摘要判定，不靠下游回写 ★

**日期**：2026-09-05
**Supersedes**：ADR-033 第 3 条、第 5 条（即 `DECISIONS_2026-09-02.md` §11.1 裁决 1）。
ADR-033 第 1、2、4 条（多候选 + 恰好一个当前版、列表接口形状、过期只标记不传播）保留。

**背景**：ADR-033 第 5 条定的是"候选按业务各建表"——首帧图候选、配音候选、
段视频候选各一张，理由是"当前版的语义按镜/段/配音各不相同"。第 3 条定的是
"下游只消费当前版，并**记录消费时用的是哪一版**"，靠 id 不一致判过期。

2026-09-05 逐条核对同行实现后，这两条都站不住：

- 关于第 5 条：同行用**一套**版本机制覆盖了资产图、分镜图、视频、音频四类。
  核对其实现后确认，`is_current` 的语义在四类上**是一样的**（同一资源下恰好一条）。
  差异在**父键**（镜号 / 段 id / 镜号）而不在语义。父键不同用一个
  `(resource_type, resource_key)` 复合键就能表达，不需要三张表 × 三套 CRUD × 三套 API。
- 他们那套里还有一个动作是我们三表方案里没有对应物的：**"付了钱但结果不要，
  回滚到上一版"**。这个动作在真实使用中很常见（出了三张图，第三张最差，要退回第二张
  且不希望第三张继续占着当前版）。
- 关于第 3 条：靠下游回写"我消费了哪一版"，要求**每一次内容写入都同步回写全部下游
  记录，漏一处就长期说谎**，而漏回写不会让任何测试变红。同行否掉了这条路，改用
  **内容摘要**：把"这个产物依据了哪些内容"取 canonical JSON 后哈希，登记在产物上；
  判断是否过期时现算一次期望摘要，跟登记的比。不需要任何回写。

**决定**：

1. **候选收成一张 `artifact_versions`**：`(resource_type, resource_key, version,
   asset_id, is_current, basis_digest, task_id, created_at)`，
   `(resource_type, resource_key)` 上加**部分唯一索引**保证 `is_current` 恰好一条。
   `resource_type` 覆盖 首帧图 / 配音 / 视频 / 角色基准图 / 场景参考图。
   `assets` 仍然只存文件与血缘，不加"变体组 / 当前版"字段（这一点 ADR-033 定得对，保留）。
2. **补上"弃用当前版"动作**：把当前版退回上一版，被弃用的那版留在库里不删。
   与"切换当前版"是两个动作：前者表达"这次生成的结果我不要"，后者表达"我选另一张"。
3. **过期改用 basis digest 判定，删除"下游记录消费了哪一版"这条路。**
   每个产物存 `basis_digest`；读的时候现算期望摘要比对。
4. **basis 的边界按"这一位是否改变用户拿到的成品内容"划，不按"它填在配置页还是写在
   提示词里"划**：
   - **视觉产物的 basis 不含 provider / model / seed / 分辨率。** 否则用户换一次出图
     模型，手里一屋子图集体判旧，逼出一轮纯重复的付费。
   - **配音的 basis 含音色与语速。** 换了音色，用户听到的成品确实变了。
   - 这条准则同时回答了 ADR-032 第 4 条留下的问题"换视频模型后段数会变，算不算上游
     变更"：按此准则**不算**，换模型不该让已生成的视频判旧。
5. `07_ASSET_LIBRARY.md`、`12_MEDIA_TIMELINE_EXPORT.md`、`06_CONSISTENCY_IMAGE.md`
   三份模块文档按本条对齐；`06` 的 FR-CONS-001 与 `12` 的候选表设计据此重写。

**原因**：第 1 条省下的不是"两张表"，是**两套 CRUD、两套 API、两套前端取当前版的
逻辑，以及三处各自演化后必然出现的语义分叉**。第 3 条省下的是一整类不会变红的 bug。
第 4 条那条准则是本次调研里最值得抄的一句话——它把"什么算变了"从一个凭直觉逐字段
争论的问题，变成一个有判据的问题。

**代价**：

- `artifact_versions` 是一张会长得很大的表（每次生成一行）。需要索引设计和清理策略，
  记进 `14_PLATFORM_OPERATIONS.md`。
- basis digest 要求"依据"本身是可 canonical 化的。取哪些字段进 basis 必须逐类想清楚
  并写进模块文档，想漏一个字段的后果是"改了它但产物不判旧"——比回写方案的失败模式
  更隐蔽，但它至少是**一处集中的定义**，而不是散在每个下游写入点。
- ADR-033 第 3 条已经写进 `06` / `07` / `12` 三份文档，要一起改。目前**没有任何代码**
  实现了候选版本，所以这次改动是纯文档级的——这也正是现在就要改的原因。

## ADR-036 提示词改由 Agent 合成；风格词由系统逐字注入且不可改写 ★

**日期**：2026-09-05
**Supersedes**：`CLAUDE.md` 不可违反的规则表里的「Agent 不许自己写风格词」一条，
以及 `17_ConsistencyEngine.md` 中"提示词一律由确定性代码合成"的相关表述。
**决策人**：负责人（2026-09-05）。

**背景**：此前的设计是——Agent 只产出结构化档案（角色外貌、场景环境、镜头画面内容），
**最终喂给出图/视频模型的那段提示词由 `consistency/compose.py` 用确定性代码拼装**，
且 `strip_style_words` 会把 Agent 自行写的风格词剥掉。理由写在硬规则表里：
"Agent 不许自己写风格词——画风漂移头号来源"。

2026-09-05 评估一份成熟的短剧生产提示词流水线（三份原始提示词合并，覆盖剧本改编、
角色场景美术指导、分镜总导演）时发现，它在同一个问题上走的是相反的路：
**让模型把档案 + 锁定的风格词合成最终提示词**。

Lead 最初的判断是"照搬会拆掉我们最重要的防线"。**负责人否决了这个判断，
裁定让模型来写提示词是对的。**

复核那份流水线之后，可以确认它并不是"放任模型自由发挥"——它自己带着一条硬约束：

> `STYLE_TOKEN_*` 在所有提示词中必须**展开为完整描述词**，严禁只写编号或名称。
> 三者（人物版 / 场景版 / 视频版）**不得混用**。

也就是说它把这件事拆成了两层：**风格词是系统给的定值，模型负责的是把定值和内容
组织成一段好的提示词**。这两层拆开之后，原先那条硬规则想防的东西（风格漂移）
仍然被防住，而模型的组织能力被释放出来。

**决定**：

1. **最终提示词由 Agent 合成**，不再由 `compose.py` 拼装。角色立绘、场景概念图、
   镜头画面、视频提示词四类都适用。
2. **风格词仍然由系统提供，且必须逐字展开**。Agent 收到的是完整描述词本身
   （不是编号、不是名称），并被要求原样写进提示词。**Agent 不得改写、精简、
   翻译或替换风格词**——这一条从"不许写"改成"必须照抄"，防的是同一件事。
3. **风格词分三套**：人物版 / 场景版 / 视频版，各注入各的，不得混用。
   理由是它们服务的对象不同：场景参考图要的是"空场景"（不能把人画进背景），
   视频提示词要的是帧率与运动质感（画静态图时是噪声）。`style_profiles` 表按此拆列。
4. **`strip_style_words` 的语义反转**：从"剥掉 Agent 写的风格词"改为
   "校验系统给的风格词有没有被原样保留"。缺失或被改写时**判定为 Agent 输出不合格**，
   走既有的审核门/重试路径，不静默放行。
5. 每一次生成仍然必存 `resolved_prompt`（既有 FR-CONS-005 不变）。
   这条在新设计下更重要：提示词现在是模型产物，不再能由代码重算出来。

**原因**：原规则把"谁来组织语言"和"谁来决定风格"这两件事绑在了一起，
用放弃前者的代价换取后者的确定性。第 2 条把它们解开：风格仍然是系统的定值，
组织语言交给更擅长的一方。

**代价**：

- 提示词不再可由代码复现，只能从 `resolved_prompt` 读回。审计与排查依赖这一列必存。
- 多了一道校验（风格词是否被原样保留），并且它会产生新的失败模式：
  Agent 反复改写风格词导致任务失败。需要在 eval 用例里覆盖。
- `consistency/compose.py` 的角色从"合成器"变成"素材准备器 + 校验器"，要重写。
- 既有的 `strip_style_words` 单测要按新语义重写。

**未变的**：一致性引擎的其余机制（项目级基准 seed + 镜号偏移、风格锁定、
参考图注入、候选版本）全部不受影响。Agent 仍然不许决定用哪个模型、不许决定花多少钱。

## ADR-037 四道门：开拍前确认、剧本、空间锚点、分镜 ★

**日期**：2026-09-05
**Supersedes**：`01_ProductSpec.md` §5 的三道门设定；`orchestrator._GATE_OF` 的两道门实现。
**决策人**：负责人（2026-09-05，批准 `project_docs/plans/2026-09-05_pipeline_ux_assessment.md`）。

**背景**：今天只有两道门——剧本门（`await_setup`）与分镜门（`await_storyboard`）。
评估一份成熟短剧生产流水线后发现它有四个强制停顿点，其中两个我们完全没有：

- **画风确认**。它把画风放在最前面，且"输出画风确认消息后必须停止一切后续动作"。
  画风一旦锁定，全程所有下游提示词都带同一套描述词。我们今天没有这个概念，
  风格是在出图时才拼进去的，用户从没被问过。
- **空间锚点卡确认**。场景的固定空间关系（门在哪、桌子在哪、摄影主轴朝哪）
  必须在生成任何镜头提示词之前一次性确认并锁定。我们的 `SceneSheet` 早就有
  `camera_axis` 与 `fixed_references` 两个字段，注释写着"构成空间锚点卡的固定层"，
  但**从来没有任何流程去填它们、更没有让用户确认过**。

另外它在同一屏还要求确认**情节目录**（"以上为本次将覆盖的全部情节，如有遗漏请告知"）
和**时代背景**（决定角色人种与场景建筑，判错会一路传导到分镜）。

**决定**：

1. **门从两道变四道**，不是五道。因为画风、改编模式、情节目录、时代背景
   **四件事发生在同一个时刻**，合并成一道门：

```
routing → plot_index →【① 开拍前确认】→ screenplay →【② 剧本门】
        → characters → scenes →【③ 空间锚点门】→ storyboard →【④ 分镜门】→ done
```

2. **门① 开拍前确认**（新增，`await_plan`）。一次停顿，四项决定：
   - **情节目录**：确认覆盖范围，可指出遗漏（打回则重跑 `plot_index`）
   - **时代背景与国籍人种**：系统按剧本内证据判定后给出，用户可改。
     **判定结果不得默认套用本国**——判错会让角色人种、服装、发型与场景建筑、
     街景、室内陈设全部错位，且错误一路传导到分镜。
   - **画风**：从画风目录里选一个，锁定后全程不再询问
   - **改编 / 洗稿**：决定 `screenplay` 阶段跑哪种改编。这是整条流水线上
     **唯一一个用户必须做的分支选择**，其余步骤都是自动的
3. **门③ 空间锚点门**（新增，`await_anchors`）。`scenes` 之后、`storyboard` 之前，
   一次性输出全部需要锚点卡的场景，用户一次确认全部（**禁止逐个确认**）。
   哪些场景需要锚点卡按客观判据决定：该场景出现 3 个及以上镜号、
   或有 2 人及以上同时在场、或场景内有明显位移——满足任一条即需要；
   都不满足的用内联描述，不单独出卡。
4. **门② 剧本门与门④ 分镜门保持不变**，包括它们的打回退回阶段。
5. **打回语义**：门① 打回退回 `plot_index`；门③ 打回退回 `scenes`。
6. **`Stage` 枚举新增两个值，这是一次数据迁移。** `_LEGACY_STAGES` 已有前例
   （2026-08-18 那次由 2 步改 5 步）。存量项目按当前阶段映射到新图上的对应位置，
   **已经越过新门的项目不得被退回去重新确认**——它们的画风与锚点按缺省值补齐并标注
   "历史项目，未经确认"。

**原因**：第 1 条是这次设计里唯一需要解释的取舍。把四件事拆成四道门会让用户在
开始生产前连点四次确认，而这四件事**在信息上是同时可决的**——都只依赖原文与情节目录，
不依赖彼此。分开只增加点击，不增加判断质量。

第 3 条的"一次性确认全部锚点卡"是照抄它的硬规则，理由也照抄：逐个确认在场景多的项目里
会变成几十次点击，而用户实际上是把它们当成一张全局的空间地图在看。

**代价**：

- 用户从上传到看见第一段剧本，中间多了一道门。这是有意的：画风与人种一旦定错，
  后面每一张图都错，而那时的返工成本是"全部重出"。
- `Stage` 枚举变更 = 数据迁移 + `_NEXT` / `_GATE_OF` / `_REDO_FROM` / `_REQUIRES` /
  `_LEGACY_STAGES` 五张表同时改。前端的阶段映射（`lib/freeflow/stage-map.ts`
  把后端阶段折成五段展示）也要跟着改。
- 门③ 依赖"锚点卡"这个产出存在，而它今天没有生产者。需要在 `scenes` 阶段
  或一个新的确定性步骤里产出它。

**未决**（不挡本 ADR）：锚点卡的动态层（每批次的人物站位）放在哪一步生成，
取决于批次概念最终怎么定，见 ADR-034 与 `12_MEDIA_TIMELINE_EXPORT.md`。

### 2026-09-07 补充：门③ 同时确认光照状态，但作用域与锚点不同

场景档案改成多个具名光照状态之后（每个场景声明它在剧里实际出现过的时刻），
出现一个问题：光照错了和锚点错了是**同一种失败**——整场戏每一张图都错，
而且要到成片剪在一起才看得出来。所以它同样该在开拍前锁定，不该等到出图。

**决定：门③ 一次确认两样东西，但两样的作用域不同，界面上必须分开呈现。**

| 确认什么 | 覆盖哪些场景 | 为什么 |
|---|---|---|
| 空间锚点固定层 | **只有出卡的场景**（判据见上文第 3 条） | 一两个镜头、单人、无位移的场景走内联描述就够，出卡是浪费 |
| 光照状态 | **全部场景，包括走内联描述的** | 光照对每个场景都成立，一镜的戏也有它的光 |

这条差异是这次裁决的全部内容。把光照挂在锚点卡上是错的——那样走内联描述的
场景永远没人确认过它的光，而它们照样要出图。

门的位置、判据、打回语义都不变；门③ 仍是一次停顿、一次确认全部。

## ADR-038 提示词可追溯与真实生成失败显式化

**日期**：2026-09-13。依据：负责人要求落实 9 月 5 日 Skill 接入、调查效果偏差并自动完成整改。

**问题**：9 月 10 日的目标项目记录包含 6 次 `mock.llm.v1` 文本运行与 4 次
`mock.image.v1` 出图。非测试环境缺少平台 Key 会自动生成占位结果；同时 ADR-036
尚未接入出图入口。占位成功掩盖了模型不可用，也让提示词质量问题无法准确归因。

**决定**：

1. `ENV=test` 保留 Mock 以验证执行流程；非测试环境不再因缺 Key 自动使用 Mock。

   最终词；任务记录运行 ID、输入摘要和规则版本。只读查看零推理，生成前可显式准备。
   上游档案或镜头变化使旧提示词过期，指定旧运行时拒绝出图；旧词仍可回看。
3. 缺场景档案或引用不存在角色的镜头报 409，不再无声忽略。现有非法光照名退回
   已声明默认光照的兼容机制保留，并记录实际采用状态。错误须指向可修正的前置数据。
