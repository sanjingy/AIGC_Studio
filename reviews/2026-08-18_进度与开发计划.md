# AIGC Studio — 进度与开发计划

> 2026-08-18。供外部评审。
> 写作原则：**能跑通的和跑不通的分开写，没验证过的不写成已完成。**

---

## 一、一句话现状

从小说到分镜的**文本链路已经端到端跑通**（真实 Provider 验证过）；
从分镜到成片的**出片链路一行没接**。核心的商业风险——单片成本——
仍然测不出来，因为废片率没有标定。

---

## 二、系统是什么

面向普通用户的 AI 内容生产操作系统。主线：**小说 → 5 分钟悬疑漫剧**。
盈亏平衡线是**每天 16 部成片**（`19_UnitEconomics.md`），所有优先级用它衡量。

### 技术栈

```
FastAPI 模块化单体 + Arq Worker + PostgreSQL/pgvector + Redis + MinIO
前端 Next.js（App Router）
Provider：DeepSeek（文本）/ 阿里云百炼万相（图像）
```

代码量：业务代码 ~9.8k 行，测试 ~3.9k 行，385 个用例。

### 三个可能被追问的架构选择

**1. 不用 LangGraph（ADR-008）。**
编排器是「读 `projects.current_state_json` → 算下一步」的纯函数，
每次从库里重算，不持有内存状态。LangGraph 的 checkpoint 会在
进程重启、Worker 崩溃、用户隔天回来续做这三种情况下各错一遍。
代价是每次推进多一次 DB 读。

**2. Agent 是声明不是代码。**
一个 Agent = 一份 YAML（提示词 + output schema + 工具白名单 +
步数/预算上限），由平台 runner 解释执行。理由：第三方 Agent 会跑在
我们服务器上、花用户 Credits、读用户项目数据，允许执行任意代码
等于把服务器交出去。

**3. 价格与系数一律参数化（ADR-014）。**
不写代码常量，走 `model_pricing` / `pricing_rules` 表。
DeepSeek 2026-08-17 高峰输出价涨了 350%——写死就是那一夜毛利转负
且必须发版才能止损。有一条 CI 用例扫 AST 强制这条。

同一个 output schema，改动由后端 diff 出来给用户看。

## 四、真正验证过什么

用《赤色博物馆》开场（717 字）跑真实 Provider，产出：

- **情节目录** 7 个节点 + 角色称呼映射表
- **剧本** 逐节点覆盖，`node_coverage` 是结构化引用（QA 能真去查那一场存不存在）
- **角色档案** 4 个，含人种/体型/五官/服装/阵营/即时状态
- **场景档案** 5 个，含**摄影主轴**（机位→朝向→远景末端）与固定参照物
- **分镜表** 27 个镜号（分镜自建 12 个节点），9 列：
  镜号/节点/景别/角度/运镜/画面/出场人物/场景/对白+音效

景别用总导演词库（中景腰部/近景胸像/中全景），角度遵守默认省略
（正面平视居中不写）。5 个原著专有名词全部命中。

## 六、已知风险（最想请教的部分）

### 风险 1：违反了项目自己定的规则 —— 新增 5 个 Agent 没有 eval

`CLAUDE.md` 写明"新 Agent 必须有 eval 用例才能上线"，
`22_AgentEval.md` 设计了 `eval_runs` / `eval_results` / `eval_baselines`
三张表。但 **`evals/` 目录不存在**，本轮新增的 5 个 Agent
（情节目录/剧本/角色/场景/分镜）一个 eval 都没有。

后果：提示词改动不会让测试变红，质量会悄悄退化，而且改坏了
没人知道是哪一次改的。**这是当前最大的工程债。**

### 风险 2：废片率没标定，报价不可用

`pricing_rules.image_retry_factor = 250` 是拍的。验证切片跑出的
3.33 无效——它把构图差异计成了废片。

`consistency/metrics.py` 的实测数据说明了为什么难：

```
不同角色 / 同镜别        0.30      ← 身份确实不同
同一角色 / 差异大的镜别   0.65–0.68  ← 远景、特写手部、多人同框
同一角色 / 相近镜别       0.81–0.84
```

**构图差异对整图 embedding 的影响，和身份差异是同一个量级。**
单一全局阈值必然误判：0.75 会把所有远景和特写都判成"角色崩了"。

现在的做法是拆成 PASS(0.78) / REJECT(0.50) 两档，中间地带交人工。
真正的解法可能是按镜别分别建基准（三视图 + 表情集），但没验证过。

**请教点：这个代理指标是不是根本不适合做废片判据？有没有更靠谱的
自动判据，还是说这件事必须人工？**

### 风险 3：分镜质量——运镜单调

27 镜里大部分是「固定镜头」。导演四定律（视线跟切镜、威胁正反打、
大动作三段拆解、说话人给近景）模型只做到一部分。

**请教点：这类"风格化程度"的提示词调优，除了堆 few-shot 还有别的
系统性做法吗？没有 eval 的情况下怎么判断改好了还是改坏了？**

### 风险 4：一次改动打死存量数据

本轮把阶段枚举从 2 步改成 5 步，忘了库里已有 41 个项目带着旧阶段名，
直接 KeyError 变 500，用户表现为"点继续没反应"。已修（旧名翻译 +
缺上游产出时自动回退），但暴露的是：**状态存在库里意味着每次枚举
变更都是一次数据迁移**，而现在没有任何机制强制这件事。

### 风险 5：成本结构未知

单片成本 = 文本 + TTS + 图像 + 视频。现在只有文本环节的真实数据。
图像环节的成本完全取决于废片率（风险 2），视频环节还没跑过。
**在这三个数字出来之前，"每天 16 部成片盈亏平衡"这条线是算不出来的。**

## 七、开发计划

### 近期（1~2 周）：先把窟窿补上，不加新功能

| 优先级 | 事项 | 判据 |
|---|---|---|
| P0 | **补 eval 用例**，5 个新 Agent 各建黄金测试集 | 提示词改动能被自动评分捕捉 |
| P0 | **上传 txt**（need.md #1） | 两万字小说能正常输入 |
| P1 | 画风确认 + STYLE_TOKEN 全局锁定 | 8 种风格可选，全程不漂 |
| P1 | 时长计算 + 15 秒批次切分 | 分镜表补齐时长/批次两列 |
| P1 | 空间锚点卡 | 同场景多镜的空间关系不乱 |

### 中期：出图接进链路 → 标定废片率

```
角色立绘出图 → 人工逐张判可用性 → 用真实数据反推废片率
                                  → 校准相似度阈值
                                  → 报价才可信
```

**这一步是解锁商业判断的前提**，比出片更优先。

### M2：出片

```
剧本定稿 → TTS 拿到真实音频时长 → 反推镜头时长 → 关键帧
        → 图生视频 → 时间线装配 → ffmpeg
```

注意顺序：**TTS 必须在视觉之前**（ADR-011）。剧本定稿时台词就定了，
此刻合成能拿到真实时长，分镜的时长和批次从第一次算就是真值。
先出视频再配音必然音画错位——片段时长固定、台词时长不固定，
事后拉伸变形、裁剪丢内容。

### 之后：Skill 运行时

把 13 个 handler 实现掉，阶段图从 `orchestrator._NEXT` 移到 Skill 声明。
这一步之前不要做，因为现在阶段图还在频繁变，固化太早只会白改两遍。

## 八、想请高人看的三件事

1. **废片率的自动判据**（风险 2）——这是成本模型的唯一未知数
2. **提示词质量的可回归化**（风险 1、3）——eval 该怎么建才不流于形式
3. **架构判断**：模块化单体 + 声明式 Agent + 硬编码阶段图，
   这个组合在"要支持第三方上传生产模板"的目标下，是不是走对了方向
