## 2. 三个判断题

### 端点挂在哪：`/projects/{id}/images`，新开 `consistency/router.py`

不挂 `/tasks`：这两个动作的入参是"画哪个角色 / 哪一镜"，提示词由系统合成，
和"随便建一个出图任务"不是同一件事。不挂 `project/router.py`：它是项目
CRUD，塞进出图会让那个文件同时依赖一致性引擎、任务和计费三个模块。
放在 consistency 模块下，权限判断只有一条路——先取项目，取不到就 404。

返回体直接用 `task.schemas.TaskOut`。出图就是一个普通任务，前端已经认识
这个形状；另造一份"出图任务"DTO 只会多一份要同步的真相。这是本次唯一一处
跨模块 import schemas（ruff 不禁止，`banned-api` 只挡 repository / models）。

### `ShotConditioning` 落库时机：**建任务时**

它回答的问题是"这一镜是拿什么去生成的"，而这个问题**在失败的时候最需要
答案**。等任务跑完再落，崩掉的那些镜头恰好一条记录都没有，而它们才是要查
的那些。提示词也确实是在建任务这一刻定下来的——Worker 只是拿着 `input_json`
去调上游，不会再改一个字，所以"打算怎么生成"和"实际用了什么"在这条链路上
是同一份数据。

代价说清楚：
- `asset_id` 留空。图还不存在，补它要改 Worker，超出本次范围；
  "这次出图产出了哪张图"由 `tasks.output_json.asset_ids` 回答。
- `POST /tasks/{id}/retry` 重试不会新增一条记录。重试用的是同一份
  `input_json`，条件化没变，多一条一模一样的记录没有信息量。
- 被取消的任务会留下一条"打算这么生成但没跑"的记录。可接受——
  宁可多一条没跑的，也不要少一条崩掉的。

### 一致性引擎写库失败：**不拖累角色阶段**

`_sync_consistency()` 放在 `_save()` **之后**，整段 try/except 兜住，
失败只记 `log.error` 不往上抛。三条理由：

1. 角色阶段的产出是一次真实的 LLM 调用，钱已经花了、结果已经入库。
   为一次写库失败把整步判失败，用户重跑就是再花一次钱。
2. 一致性资产包是可补的：出图端点在合成提示词之前会用**同一个函数**
   再同步一次（`ensure_style` 已存在不覆盖、`upsert_characters` 已冻结
   不覆盖，两个都幂等），所以这里漏了不会变成死局。
3. 阶段推进的唯一真相是 `projects.current_state_json`，它在上一行已经
   提交过了。这里再抛异常只会制造"状态已经推进了但接口报错"这种更难解释
   的状态。

**但不静默**：`log.error("agent.consistency_sync_failed", ...)` 留下真正的
原因，否则用户点"生成基准立绘"拿到前置条件错误时无从查起。

顺带一个副作用是好的：出图端点里的这次补齐同时解决了**存量项目**——
它们跑过角色阶段但库里没有任何档案，接线之前的项目照样能出图。

## 4. 顺带发现的既有问题（没改）

`visual.character.v1` 会把中文人名直接当 `ref`。第一次真机跑用了
「绯色冴子」这个名字，模型三次都输出 `ref: "绯色冴子"`，撞
`^[a-z][a-z0-9_]{1,30}$` 校验，三次重试全废，**整个 advance 返回 500**。
换成「林舒 / 陈海」就正常给出 `lin_shu` / `chen_hai`。

这不是本次改动引入的，也不在任务范围内，但它意味着：日文名、生僻字的原著
会在角色阶段直接把项目卡死，且用户看到的只是"服务暂时不可用"。
修法大概是让 Agent 在拿不准时用 `char_1` 这类兜底 ref，或者在 runner 里
把非法 ref 规范化——两条都要动提示词或 schema，建议单开一个任务。
