# 资产库文件夹 + 参考描述生成角色 —— 交付报告

**日期**：2026-08-19
**范围**：借鉴 AgentCine 的两项能力，加到上一轮的资产库上。
**未做**：appearances（同一角色多套外观变体）——依赖真实出图，出图还没接进
生产链路，按任务书要求留到 M2 之后。

---

## 一、做了什么

### 1. 文件夹（Folders）

用户能在资产库里建文件夹，把**四类东西**归进去：图片/视频（`assets`）、
项目里的角色/场景档案（`agent_runs`）、独立角色档案（新表）。
不带 `folder_id` 的"全部"视图与加文件夹之前完全一致（按项目分组的档案 +
分页的资产），只是每条多带一个 `folder_id` 标签。

- `GET /assets/folders`、`POST /assets/folders`、`PATCH /assets/folders/{id}`、
  `DELETE /assets/folders/{id}`
- `PUT /assets/folder-items` —— 归类/移出（`folder_id: null` = 移出）
- `GET /assets/library?folder_id=…` —— 文件夹视图

### 2. 一段描述 → 一份角色档案（Reference-to-character）

`POST /assets/characters`，输入一段角色描述（上限 6000 字），跑出一份与
`visual.character.v1` 完全同构的 `CharacterSheets`，存进资产库，
**不挂任何项目、不需要先建项目**。配套 `GET/DELETE /assets/characters[/{id}]`。

## 二、两个关键判断

### 复用 `visual.character.v1`，没有新增变体 Agent

输入形态不同（参考描述 vs 剧本），但要产出的东西完全一样——同一个
`CharacterSheets`、同一套"先分析性格再推导外观""禁止写画风"的规则。
两份相似的角色提示词一定会分叉，而这正是 ADR-020 拆三份提示词时要避免的
失败模式（拆开的是**职责不同**的提示词，不是同一职责的两个副本）。

输入形态的差异由 `system_suffix` 抹平（`runner.run_agent` 文档里写明这个参数
就是"改变任务性质而不换 Agent"用的，聊天修订用的也是它）：告诉模型这次
不是剧本、**不要虚构描述里没有的角色**。真机验证时用真实 deepseek-chat 跑，
一段单人描述产出了恰好一个角色，没有编出配角。

顺带：`runner` 拆出了 `complete_structured`（提示词合成 + 输出契约 + schema
校验 + 重试，**不碰数据库**），`run_agent` 在它外面套一层落
`agent_runs`/`agent_steps`。不挂项目的调用只用内核那一半。spec 的四重约束
一条都没被绕开，两条路径共用同一套提示词逻辑。

### 独立角色档案另起 `character_entries`，没有动 `agent_runs.project_id`

那一列是 NOT NULL，且资产库、项目详情、编排器全都按项目查它。松掉这条约束
等于让所有"按项目查档案"的代码重新考虑 NULL 的语义——为一个新入口去动一条
被四处依赖的约束，风险远大于多一张表（任务书也点明冲突时以新表为准）。
表里存了 `resolved_prompt` 全文（与 `agent_steps` 同一个理由：
17_ConsistencyEngine.md §7，没有它查不清产出为什么崩）。

归类关系同理走独立的 `asset_folder_items`，**没给任何现有表加列**：
要归类的还有角色/场景档案，那在 agent 模块的表上，asset 模块不能往别人的表上
加列（ADR-009）。

## 三、计费

同步 Agent 调用照常走 reserve → settle，**没有绕过计费**：

- **预扣** = spec 的 `budget_credits`（`visual.character.v1` 是 400）。
  它本来就是"单次运行成本上限"，用它当预扣额不需要再引入一个新数字。
- **结算** = 按实际输出 token 查 `model_pricing`，差额退回。
- 流水的 `ref_type` 记 `character_entry`（新加的可选参数，默认仍是 `task`）。
  写 `task` 会指向一个不存在的 task 行，对账时查不下去。
- 失败走 `release`，一分不扣。余额不足在**调模型之前**就被拦下（402）。

**过程中改掉了一个真实的漏收**：结算原本向下取整。真机跑一次真实
deepseek-chat 的结果是 —— 约 600 个输出 token × 每百万 400 Credits = 0.24，
取整之后**结算金额是 0**。改成不足 1 Credit 按 1 收（整数向上取整，不引浮点），
再跑一次真机：`reserved=400 → cost=1`，余额 500 → 499，reserved 归零。
补了回归用例守住这条。

## 六、偏离与遗留

- **多改了一处不在任务书里的东西**：结算的取整方式（向下 → 向上）。
  不改的话这条入口会 100% 收 0，等于"绕过计费"，与任务书"不能绕过计费"
  直接冲突，所以就地修了并补了用例。它同时影响将来所有走
  `text_run_cost` 的调用（目前只有这一条）。
- **孤儿归类行**：归类关系与被归类的东西之间没有外键（跨模块不能加）。
  删角色档案时会顺手清理，删资产时不会——孤儿行不影响展示（列表从实体侧
  查出来再打标），但需要一个定期清理任务，记在 ADR-028 的代价里，留给 M2。
- **文件夹视图不分页**，容量由 `MAX_FOLDER_ITEMS`（2000）封顶。先分页再按
  归类过滤会得到一页空结果，比不分页糟。
- **测试套件有一条既有的偶发失败**：`test_worker_finish_ignores_cancelled_task`
  在一次全量运行里因 `reserved` 被扣成负数而失败，单独重跑 3 次、全量重跑
  一次都通过。原因是 worker 容器的常驻中继与用例并发处理同一个被取消的任务，
  导致重复 release —— 与本轮改动无关（本轮对 billing 的改动只有一个默认值
  不变的 `ref_type` 参数，不涉及金额与幂等键）。留一个观察点。
- 真机验证在本地开发库里留下了一个 `smoke-*@example.com` 账号和两份角色档案。
