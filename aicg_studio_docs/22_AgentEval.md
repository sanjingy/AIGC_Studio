# Agent 质量评估与回归

> 这是 AI 产品最容易漏、代价最大的一块。
>
> 传统软件改一行代码，测试会红。
> Agent 改一行 prompt，测试全绿，**质量悄悄崩了三个月才被用户投诉发现**。

---

## 1. 需要防住的退化

| 场景 | 后果 |
|---|---|
| Router 提示词微调 | 路线判断准确率从 92% 掉到 70%，用户进错流程 |
| 更换 LLM 或版本升级 | 结构化输出格式漂移，下游解析全崩 |
| Prompt Agent 调整 | 出图质量下降，废片率从 2.5 涨到 4.0，成本涨 60% |
| 分镜策略调整 | 镜头数暴涨，单片成本翻倍 |
| 上游模型静默更新 | 什么都没改，效果变了 |

最后一条尤其可怕：**你没改任何代码，供应商改了模型。**
没有回归集，你永远不知道发生了什么。

## 2. 黄金测试集（Golden Set）

### 2.1 Router 层

50 条真实用户输入 + 人工标注的正确路线。

```yaml
- input: "把这篇小说做成 5 分钟悬疑漫剧"
  expect_route: NOVEL_TO_ANIME
  expect_clarification: false

- input: "做个视频"
  expect_clarification: true      # 信息不足必须追问

- input: "把这张图变成会动的"
  expect_route: IMAGE_TO_VIDEO
```

**指标**：路线准确率 ≥ 90%，追问召回率 ≥ 85%（该问的时候要问）。

### 2.2 结构化输出层

对每个 Agent，验证输出能被 Pydantic schema 解析。

**指标**：schema 通过率 = 100%（一次通过率 ≥ 95%，允许 1 次重试后达 100%）。
这一项是**硬门禁**，不达标不允许发布。

### 2.3 内容质量层

10 个固定的输入样本（不同题材的小说片段），跑完整链路到分镜。

评分方式：**LLM-as-judge + 人工抽检**。

```yaml
rubric:
  story_structure:    # 故事结构完整性
    - 是否有清晰的起承转合
    - 冲突是否明确
    - 是否适配目标时长
  character_extraction:
    - 主要角色是否无遗漏
    - 外貌描述是否足够具体到可以出图
    - 是否存在角色混淆
  storyboard:
    - 镜头数是否在合理区间（目标时长 / 5s ± 30%）
    - 是否有景别变化
    - 每镜头提示词是否可直接用于生图
```

**指标**：各维度平均分 ≥ 3.5 / 5，且无单项 < 2.5。

> LLM-as-judge 本身也会漂移。评分模型必须**锁定版本**，
> 每季度用人工评分校准一次评委模型。

### 2.4 一致性层

与 `17_ConsistencyEngine.md` 第 6 节共用指标：
角色相似度、风格一致性、时序稳定性。

固定 3 个角色 × 10 个镜头的基准集，每次改动后重跑。

### 2.5 成本层

**这一项经常被漏，但它直接对应真金白银。**

跑完基准集后统计：

```text
平均镜头数
平均图片生成次数（废片率）
平均视频生成次数
平均 LLM token 消耗
折算单片成本
```

**门禁：单片成本回归 > 15% 视为失败**，即使质量分数没降。
质量提升 5% 但成本涨 40% 是一笔坏买卖，必须显式决策而不是悄悄发生。

## 3. 执行时机

| 时机 | 跑什么 | 耗时 |
|---|---|---|
| 每次 PR | Router 集 + schema 校验（用便宜模型） | < 3 分钟 |
| 每次合并到主干 | 全部内容质量集（Mock 图像/视频） | < 15 分钟 |
| 每周定时 | 全链路含真实生图 + 一致性指标 + 成本 | ~1 小时，成本约 ¥50 |
| 更换/升级模型前 | 全套 + 人工抽检 | 半天 |

**每周定时跑真实链路是必须的**，它是发现"上游静默更新"的唯一手段。
每周 ¥50 是这个项目里性价比最高的一笔支出。

## 4. 结果存储与对比

```text
eval_runs
  id, git_sha, model_config_snapshot, started_at, finished_at

eval_results
  run_id, suite, case_id, metric, value, passed

eval_baselines
  suite, metric, baseline_value, updated_at, updated_by
```

要求：

- 每次 run 与 baseline 自动对比，生成差异报告
- 差异报告贴到 PR 评论（含成本变化）
- baseline 更新必须人工确认，不允许自动"接受当前结果为新基线"
  （否则会温水煮青蛙式退化）

---

## 5. 与 Mock 的关系

`13_CodexDevelopmentGuide.md` 第 5 节要求 Mock First。评估体系要区分：

```text
Mock 模式  → 验证【流程正确性】：状态机、审核门、计费、错误处理
真实模式  → 验证【内容质量】：一致性、成本、审美
```

两者都要有，但不要混。用 Mock 验证质量毫无意义，
用真实模型跑每个 PR 会破产。

---

## 6. 最低可用版本

不要一上来建完整评估平台。M1 阶段只需要：

```text
1. 一个 pytest 文件，跑 20 条 Router 用例，断言准确率
2. 一个 schema 校验测试，覆盖所有 Agent 输出
3. 一个 JSON 文件记录每次的分数，用 git 追踪变化
```

三样东西，一天能做完，能挡住 80% 的退化。
剩下的等有了真实数据再建。
