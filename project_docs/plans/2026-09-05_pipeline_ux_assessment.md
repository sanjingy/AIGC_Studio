# 从上传到镜头：确认点与提示词落点（Lead 评估）

> 负责人 2026-09-05 提出：用户从上传文本开始，按 Skill 的 A/B/C 一步步生成项目资产，
> 每个确认点弹框让用户确认；空间/站位类提示词放项目总览，角色/场景/镜头类各放各页。
>
> **这份是评估，不是实施方案。** 落点直觉对，四处建议改。

---

## 1. 先把两边的确认点摆平

**Skill 的强制停顿**（SKILL.md + C-分镜总导演.md）：

| # | 停在哪 | 停下来干什么 |
|---|---|---|
| 1 | 剧本上传检测之后 | 确认**画风**（①~⑧）。"必须停止一切后续动作" |
| 2 | 同上一屏 | 确认**情节目录**（"如有遗漏请告知"） |
| 3 | C1 分镜表之后 | 确认分镜表 |
| 4 | C2/C3/C4 之前 | 确认**空间锚点卡**（一次性输出全部，禁止逐个确认） |
| 5 | C3 之前 | 问场景参考图 |

**我们今天的门**（`orchestrator._GATE_OF`，两道）：

```
routing → plot_index → screenplay →【setup 门】→ characters → scenes → storyboard →【storyboard 门】→ done
```

**差集很清楚**：我们缺 **画风门**（而且它应该在最前面）和 **锚点卡门**。
情节目录我们有产出但没有门，Skill 在同一屏让用户确认它。

## 2. 建议改的四处

### 2.1 空间锚点卡不该放总览，该拆成两半

锚点卡本身分两层，这两层的生命周期完全不同：

- **固定层**（这个房间的门在哪、桌子在哪、窗朝哪边）= **场景的属性**，
  一次确定，整个项目不变。→ **场景页**。
  我们的 `SceneSheet` 已经有 `camera_axis` 和 `fixed_references` 两个字段**空着等它**，
  字段注释原文就写着"构成空间锚点卡的固定层"。
- **动态层**（这一批里谁站在哪、朝向哪）= **随批次/镜头变**。→ **镜头页**。

放总览会让两层都离开各自的上下文：改场景布局时看不到场景档案，
调人物站位时看不到镜头。而且更根本的问题是——

> **总览一旦变成能编辑提示词的地方，它就不再是总览。**

总览的价值是"一眼知道现在什么状态、下一步该干什么"。它今天做到了这一点
（依赖图 + 就绪/缺失计数 + 待办门）。往里塞工作面会毁掉这个价值。

### 2.2 总览该放的是"项目级锁定变量"

你说"根据功能放总览"这个直觉是对的，但正确的外延不是空间站位，而是
**一次锁定、后面所有阶段都要读的全局量**：

| 放总览 | 为什么 |
|---|---|
| 画风（①~⑧ + 当前锁定的三套描述词） | 全项目唯一，所有下游提示词都带它 |
| 时代背景 / 国籍人种（ERA_TOKEN） | 同上，且它决定角色人种和场景建筑 |
| 情节目录 | 覆盖核验的索引，剧本和分镜都要对着它自查 |
| 角色称呼映射表 | 防止昵称/代号导致台词归属错乱 |
| 制作评估（场景数 / 台词时长 / 画面时长 / 建议集数 / 预估 Credits） | 项目级的量，且是用户决定"要不要开始花钱"的依据 |

这些正好就是 Skill 里那张 GLOBAL STATE 表中**跨阶段贯通**的那几个变量。
总览 = 项目的锁定状态与进度，不是工作面。

### 2.3 不要把 13 个技能做成菜单

A1 / B3 / C2 这种编号是**聊天体的产物**——因为聊天里没有别的导航方式，只能报编号。
产品里用户不知道 B3 是什么，也不该知道。

13 个技能落到我们这里分两类：

- **绝大多数是自动步骤**，用户根本不需要选。剧本解析、角色档案、场景档案、
  分镜表都是流水线上的一环，我们已有的"推进生产"就是它。
- **只有一处是真分支**：**A1 改编 vs A2 洗稿**。这是用户必须做的选择
  （保留原角色场景，还是替换成全新原创），而且它决定后面所有产出的性质。
  → 放在**上传文本那一步**问，和画风一起。

顺带一条合规提醒：A2 洗稿的定位是"把别人的小说深度改写成全新原创"。
个人用是一回事，**平台提供这个能力**要不要设边界，属于模块 13 的范围，
这里只做记录，不挡当前工作。

### 2.4 确认方式要分两种，不能一律弹框

判据一句话：

> **一句话能说完的决定用弹框；要读一屏以上的内容，在内容自己的页面上开门。**

| 确认点 | 形态 | 在哪 |
|---|---|---|
| 画风（8 选 1） | **弹框** | 上传后立刻 |
| 改编 / 洗稿 | **弹框**（与上一条同屏） | 上传时 |
| 情节目录（可能几十条） | 页内门 | 故事页 |
| 剧本 | 页内门（**已实现**） | 故事页 |
| 分镜表（10 列 × N 行） | 页内门（**已实现**） | 镜头页 |
| 空间锚点卡（全部场景一次出） | 页内门 | 场景页（固定层）+ 镜头页（动态层） |

理由：情节目录、分镜表、锚点卡这三样塞进模态框都没法看，更没法边看边改。
而我们**已经有两个跑通的页内门**（剧本门在故事页、分镜门在镜头页，
2026-09-05 在服务器上完整验过），新的门照这个模式做即可，不用发明第二套。

## 3. 一个你没提、但会决定产品形态的问题：提示词要不要给用户看

这份 Skill 的**最终产物就是提示词**——因为它假设用户把提示词复制到即梦 / Nano Banana
里自己去生成。我们不一样：**我们自己调模型生成**。

所以有一个岔路：

- **如果把每段提示词做成一等公民摆在页面上**，我们就变成了一个提示词生成器，
  用户还是要自己去别处生成。那正是我们本来要替他消除的工作。
- **如果完全不给看**，用户不知道"为什么画成这样"，出了问题也没法排查，
  而且我们刚做完的字段级编辑会显得莫名其妙——改了字段，看不到它怎么影响提示词。

**建议**：提示词可见但不是主角。放在每个资产的详情/检视区，**可复制、默认只读**，
作为"这一张是按什么生成的"的交代与排查手段；主操作永远是「生成」而不是「复制提示词」。

**是否可编辑是另一个决定**，而且代价不小：提示词一旦可编辑，它就进了产物的依据
（ADR-035 的 basis digest），改了要判过期、要记修订、要能撤销——
等于给提示词再做一遍我们刚给分镜做的那一套。建议先只读，等看到真实需求再说。

## 4. 综合下来的形态

```
上传文本
   ↓
【弹框】改编 / 洗稿  +  画风 ①~⑧        ← 短选择，弹框合适
   ↓  （系统同时算出情节目录、时代背景、制作评估）
项目总览：锁定变量 + 制作评估 + 依赖图     ← 看状态，不干活
   ↓ 推进生产
故事页：情节目录门 → 剧本门               ← 页内门（剧本门已实现）
   ↓
角色页：角色档案 + 立绘提示词 + 出图
场景页：场景档案 + 锚点卡固定层 + 概念图提示词 + 出图
   ↓
镜头页：分镜表门 → 锚点卡动态层 → 逐镜提示词 + 出图
```

每一页放的是**那一页的资产、那一页的提示词、那一页的门**。
总览放的是**全项目共享的锁定量**。这两条规则能解释上面每一个落点。

## 5. 需要新增的后端能力（本文档只列，不实施）

1. **画风门**：新阶段 + 新门，在 `routing` 之前或与之合并。
   注意 `_LEGACY_STAGES` 的教训——改阶段枚举就是一次数据迁移。
2. **情节目录门**：`plot_index` 之后加一道门。
3. **锚点卡门**：`scenes` 之后、`storyboard` 之前。
4. `style_profiles` 拆三套描述词（人物/场景/视频），并在项目创建时锁定。
5. `CharacterSheet` 补国籍/人种；`SceneSheet` 的两个锚点字段真正填上。
6. 提示词作为产物存起来并可读（`resolved_prompt` 已有，但今天没有读它的接口）。

门从 2 道变成 5 道，这是这次改动最大的结构性影响，需要负责人确认再动。
