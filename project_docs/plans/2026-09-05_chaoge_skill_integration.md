## 1. 它是什么

一份把三位作者的提示词（小说改编大师 v2.31、角色场景美术指导 v2.1、分镜总导演 v4.3）
合并成的流水线，13 个技能分三层：

| 层 | 技能 | 产出 |
|---|---|---|
| A 剧本 | A1 改编 / A2 洗稿 | 标准短剧剧本 |
| B 美术 | B1 解析 / B2 角色档案 / B3 角色立绘提示词 / B4 场景档案 / B5 场景概念图提示词 / B6 台词SRT / B7 封面 | 档案 + 可直接投喂绘画工具的提示词 |
| C 分镜 | C1 分镜表 / C2 逐镜视频提示词 / C3 批次视频提示词 / C4 九宫格关键帧 | 9 列分镜表 + Seedance/Nano Banana 提示词 |

它的核心机制有三条：**画风只确认一次**（STYLE_ID ①~⑧，自动派发人物/场景/视频三套描述词）、
**全局变量跨阶段贯通**（ERA_TOKEN、TONE_TOKEN、情节目录、角色称呼映射表、空间锚点卡）、
**时长按公式算不许估**。

## 2. 一条被推翻的架构分歧（ADR-036）

我们和它此前有一条根本分歧：

> **它让模型写提示词，我们让代码写提示词。**

它的 B3（角色立绘）、B5（场景概念图）、C2/C3（视频提示词）、C4（九宫格）
都是让模型把档案 + 画风词合成最终提示词。我们此前的硬规则是
「Agent 不许自己写风格词——画风漂移头号来源」，提示词由 `consistency/compose.py`
确定性拼装。

**负责人 2026-09-05 裁定：它是对的，应该让模型去跑提示词。** 已立 ADR-036。

复核之后可以确认，它并不是放任模型自由发挥——它自己带着一条硬约束：
`STYLE_TOKEN_*` **必须展开为完整描述词，严禁只写编号或名称**，且人物/场景/视频
三套**不得混用**。也就是说它把这件事拆成两层：**风格词是系统给的定值，
模型负责把定值和内容组织成一段好提示词**。原先那条规则想防的漂移仍然被防住，
而模型的组织能力被释放出来。

落到我们这里的具体形态（ADR-036 第 2、4 条）：

- Agent 收到的是**完整风格描述词本身**，不是编号也不是名称；
- Agent 必须**原样照抄**进提示词，不得改写、精简、翻译或替换；
- `strip_style_words` 语义反转：从"剥掉 Agent 写的风格词"改成
  "校验系统给的风格词有没有被原样保留"，缺失即判定输出不合格，走审核门/重试。

## 4. 三处它比我们强、且我们能直接受益的

### 4.1 画风要三套描述词，不是一套

它的 `STYLE_TOKEN` 分**人物版 / 场景版 / 视频版**，同一个编号派发三套不同的词，
并且写死"三者不得混用"。理由很实在：角色立绘要"真人演员质感"，
场景要"高质量实景空场景"（**空**场景——不能把人画进背景图），
视频要"24fps 电影帧率、轻微手持晃动感"（时间维度的词，画静态图时是噪声）。

我们今天的 `style_profiles` 是**一套词全场通用**。这是一个具体的、可立即修的缺陷：
用同一句"电影级布光"去要一张场景参考图，模型很可能给你画上人。

### 4.2 时代背景决定人种，且必须显式判定

它的 `ERA_TOKEN` 在最开始就从剧本内证据判定国别 + 时代，强制注入角色档案的"国籍/人种"字段，
并且专门写了一条**"表中的中国是判定结果之一，不是兜底默认"**，
理由是"擅自改成中国，会让立绘的人种、服装、发型与场景的建筑、街景、室内陈设全部错位，
且错误会一路传导到分镜"。

我们的 `CharacterSheet` **没有国籍/人种字段**。日系原作跑出来的角色长什么样，
今天完全靠模型自由发挥，而且每次可能不一样。

### 4.3 性格 → 外观的映射表

它给了一张"强势/权力型 → 眉骨立体、眼神锐利、服装整洁有质感"这样的映射表，
外加一套身材词库并规定**必须从词库里选，不许用"匀称""普通"这种模糊词**。
这直接对应我们一致性引擎的目标：**外貌描述必须是可复现的有限词表，不是自由文本**。

我们今天的角色档案字段是自由文本，同一个角色两次生成可能一次"身材匀称"一次"体型适中"，
而这两句话喂给出图模型会得到不同的人。

## 5. 时长引擎：它填上了 ADR-034 缺的那一半

它的公式（`时长与排版铁律.md`）：

```
台词基准秒 = ceil(汉字数 ÷ 4)        只数汉字，不含标点与方括号内的动作描述
动作秒     = 简单 2 / 中等 3~4 / 复杂 5~8 / 空镜 3~4（空镜无对白加成）
最终时长   = 台词基准秒 + 动作秒，向上取整
下限       = 默认 2 秒，情绪特写 4 秒
```

**这正是我们缺的东西。** ADR-034 定的是 `duration_input = max(计划时长, 配音真实时长)`，
但"计划时长"从哪来我们一直没定义——TTS 还没接，分镜阶段又必须知道每镜多长。
这套公式给的就是那个计划值，而且它是**确定性的**（数汉字），符合我们
"时长不让模型填"的既有决定（`agents/schemas.py:415` 的注释原文就是这么写的）。

**注意一个矛盾**：我们的 `StoryboardShot` 注释说"批次由 15 秒规则切分"——
15 秒这个数正是从这套提示词来的（它是 Seedance 的批次上限）。
但 ADR-034 已经把镜内切段降级为待定。这两处需要对齐，见 §7。

## 6. 九宫格：两个独立来源撞上了

它的 C4 是"一次出 3×3 大图，每格是一个关键帧，切格后逐镜走图生视频"。
2026-09-05 的同行代码库调研**独立地**得出了同一条建议（一次出图产出 N+1 个关键帧，
天然同画风同角色，且比逐张出图便宜）。

两个来源指向同一个机制，这是很强的信号。但**我们一次都没实测过万相能不能画出对齐的无边框宫格**，
在验证之前不要写进 ADR。这是 §9 待验证清单的第一条。

## 7. 15 秒：暂按它的来，但最大时长必须由模型决定

**负责人 2026-09-05 裁定**：单次生成的最大时长应当**按模型判别**——有的模型出不了 15 秒，
有的能出 30 秒。**当前暂定 15 秒，按这份 Skill 的规则走。**

这条与 ADR-034 完全一致，而且是它的一个实例：ADR-034 已经定了模型能力要声明成
`supported_durations`（非空离散集合），并禁止任何隐性兜底。所以落地形态是：

- 15 秒**不是常量**，是"当前默认模型的档位上限"这个值今天恰好等于 15。
  它要走配置或模型目录，**不许写死在代码里**（否则换模型就要发版，撞硬规则第 1 条）。
- 计算批次/镜时长时读的是当前项目所选视频模型的 `supported_durations`，
  取其最大值作为上限；解析不到就报错，不许 fallback 到 15。

### 仍需负责人确认的一个问题

它的 C3「批次版」是把**多个镜头合并进一次 15 秒生成**（逐镜累加，超过 15 秒就开新批次）。
而 ADR-032 定的是**每个镜头一条独立 MP4**，目的是让用户拿到可自行拼接的素材。

这两条不能同时成立：一次生成覆盖三个镜头，就没法给每个镜头一条 MP4。

「按他的来」如果指的只是"最大时长 15 秒"，那没有冲突，ADR-032 保持不变。
如果指的是连"多镜合并成一批"一起采纳，那 M2 的交付物就从"每镜一条 MP4"
变成"每批一条 MP4"，这是产品形态的改变，需要明确一句。

**Lead 的建议是保持 ADR-032（每镜一条）**，理由：批次合并是迁就上游计费与调用次数的
成本优化，不是产品需求；而 ADR-034 已确认主力模型（wan2.7 2~15 秒、wan3.0 2~30 秒、
Seedance 4~15 秒）下一个镜通常一次生成就够，合并省不下几次调用。

顺带：`agents/schemas.py:415` 的注释目前写着"批次由 15 秒规则切分"，
这句在 ADR-034 之后已过时，要一并改。

## 8. 建议的执行顺序

**第一波（不依赖任何未决事项，直接可做）**

0. **ADR-036 的落地**：新增三个提示词 Agent（角色立绘 / 场景概念图 / 镜头画面），
   `consistency/compose.py` 从"合成器"改成"素材准备器 + 风格词校验器"，
   `strip_style_words` 按新语义重写并改单测。这一条是下面几条的地基。
1. `style_profiles` 拆成人物 / 场景 / 视频三套描述词，各注入各的 Agent。
   这一条独立成立——即使不接这份 Skill，"给场景参考图的提示词里带人物质感词"也是个 bug。
2. `CharacterSheet` 补 `nationality` / `ethnicity` 字段，并在 `visual_character.yaml` 里
   规定必须从剧本内证据判定、禁止默认套用本国。
3. 角色外貌字段从自由文本收紧为**有限词表**（身高/体型/体态各一个枚举）。
   这是一致性引擎的地基，`reference_embedding` 至今为空就是因为没有可比的结构化描述。

**第二波**

4. 四份 Agent 提示词的增强（screenplay / character / scene / storyboard）。
5. 导演铁律（POV、正反打、大动作拆解、台词特写）与切镜下限进 `visual_storyboard.yaml`。
   **注意**：这会让镜头数显著增加，直接影响每集成本，要先算一遍单集经济性。

**第三波（M2）**

6. 时长引擎落成确定性代码，作为 ADR-034 的"计划时长"。
7. 空间锚点卡填进 `SceneSheet` 已有的 `camera_axis` / `fixed_references`。
8. 九宫格：先实测，再决定。

## 9. 待验证清单（都要花钱，等负责人批准）

1. 万相能否画出对齐、无边框的 3×3 宫格。决定九宫格路线是否成立。
2. wan2.7 是否真的接受 2~15 秒任意时长（ADR-034 的前提，来自二手资料）。
3. 导演铁律全开之后，一集的镜头数与成本变成多少。
