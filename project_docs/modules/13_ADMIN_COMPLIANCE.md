## 1. 模块目标与边界

给商业化运营提供用户、任务、成本、模型和风险的管理面，
并满足内容审核、AIGC 标识、实名等最低合规要求。

**本轮的边界非常窄**：决策记录 §1 把**运营后台**和**合规审核**同时列入
"明确不做（M2 内）"。所以这份文档的作用不是排期，而是三件事：

1. 诚实记录**现在真的有什么**（几乎没有），防止别的文档把预留列写成能力；
2. 记录**哪些点位事后补代价极高**，让 Wave 2 写代码时别把路堵死；
3. 把需要负责人拍板的合规问题列出来（§9），因为它们有法律面，Lead 定不了。

**不拥有**：账本（模块 09）、任务状态（模块 08）、模型价格（模块 05 / 09）。
后台永远**不得绕过业务 Service 直接改业务表**——尤其不得直接改
`tasks.status`（ADR-008）或 `credit_accounts.balance`。

## 2. 用户与使用场景

本模块的用户不是创作者，是我们自己：

- **负责人**：给首批用户手动加 Credits（这条今天走 `POST /credits/topup`，
  收口方案在 [09_BILLING_PAYMENT.md](./09_BILLING_PAYMENT.md) §7.1）。
- **运维**：任务失败率高的时候查是哪个 Provider 在抖。
- **未来的财务 / 风控 / 客服**：M3 之后才存在。

M2 内这些人一共只需要一件事：**能查、能手动加额度、动作有记录**。
其余全部推到 M3。

## 5. 权限模型（设计，未实现）

做的时候按角色 + 显式 permission，不要只靠一个 `role=admin`：

| 角色 | 能做 | 不能做 |
|---|---|---|
| support | 查用户、查任务 | 改账、改内容 |
| operator | 重放任务、配模型价格 | 改账、看完整 Provider Key |
| finance | 退款 / 调账 | 改模型执行 |
| risk | 禁用内容 / 用户 | 改账 |
| admin | 授权上述角色 | — |

三条职责分离是硬要求：**财务不能改执行，风控不能改账，运维不能看 Key**。
Provider Key 在任何角色下都**永远不可回显**（ADR-025 / 027 的直接推论）。

管理端与用户端必须分离路由与 Cookie Audience——
同一把 Access Token 既能调 `/api/v1/projects` 又能调 `/admin/*`，
等于把后台的攻击面并进了用户端。

## 9. 当前缺口与风险

1. **`POST /credits/topup` 今天对所有登录用户开放**，这是目前最大的
   财务风险，但它的修点在模块 09，不在这里。
2. **没有管理员身份，也没有审计。** 在做支付之前必须先有这两样——
   一个没有审计的调账入口比没有调账更危险。顺序不能反。
3. **AIGC 标识事后补的代价是存量内容全部重渲染。** `18_Compliance.md`
   把这一条列为最贵的返工项。本轮决定不做，代价被明确接受；
   但模块 12（媒体合成）在 Wave 2 写 ffmpeg 管线时**应当预留一个
   水印注入点的位置**（不实现），否则将来要动的是已经跑通的合成链路。
   这是本文档对 Wave 2 的唯一请求。
4. **审核 hook 的位置同理**：Gateway 的调用链上事后插一个 pre/post hook
   要改所有 Provider 调用路径。`gateway/service.py::_call` 是唯一入口，
   位置天然存在，不需要现在写空壳。
5. **时间线已定（决策记录 §12.1）**：服务器在香港、域名不在大陆解析，不做 ICP 备案；
   **AIGC 标识在模块 12 的合成管线里现在就做**（可见水印槽位 + 元数据），不等本模块；
   算法备案在开放注册前做一次法律咨询后再定；实名认证不做，直到备案要求它。
6. **合规上线前需要法律复核**：算法备案、生成式 AI 服务备案的触发条件、
   AIGC 标识的具体形式、未成年人保护——这些不是工程能定的，
   `18_Compliance.md` 的 TODO 清单一条都没被勾掉。见 §9 之外的"待负责人确认"。
6. **`assets.moderation_status` 恒为 `pending`**。前端拿到了这个字段
   但没有显示——**保持不显示**。显示它等于对用户宣称有审核流程。

## 10. 迭代计划

1. **M2 期间**：什么都不做。只保证两件事——`topup` 收口（模块 09）、
   模块 12 预留水印注入点的位置。
2. **M3 第一步**：平台管理员身份 + 审计日志 + 管理端路由隔离。
   这一步必须先于支付。
3. **M3 第二步**：只读看板（用户、任务、成本、Provider 健康）。
4. **M3 第三步**：支付订单 / 退款 / 对账（依赖支付上线）。
5. **M3 第四步**：输入 / 输出审核接入与人工复核队列。
6. **M3 第五步**：AIGC 标识、实名、留存策略——按正式运营地区的法律要求补。

## 11. 验收标准和测试

M2 内本模块**没有验收项**，因为它没有交付物。下面是做的时候的标准，
现在写下来是为了将来不用重新想：

- 任一后台写操作都有不可篡改的审计记录，含操作者、原因、trace_id。
- 管理员无法通过后台绕过账本直接改余额——
  尝试直接 UPDATE `credit_accounts` 的路径在代码里不存在。
- 管理员无法直接改 `tasks.status`（ADR-008）。
- 财务、风控、运维权限互相隔离，且任何角色都读不到 Provider Key 明文。
- 被拒绝的内容不能进入公开导出流程。
- 管理端与用户端的令牌不通用。

**M2 内唯一要验的一条**（属于模块 09，在这里记一笔是因为它是本模块存在的
唯一现实理由）：普通登录用户调用 `POST /credits/topup` 返回 404，且余额不动。
